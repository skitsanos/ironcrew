# IC-026 — Image attachments are silently dropped by the Responses provider

## Finding

Conversation image attachments are a documented feature (`docs/chat.md`) and are
threaded through `run_turn(..., images)`. The Anthropic and Chat Completions
providers serialize them, but `OpenAiResponsesProvider` does not: the user
message branch in `src/llm/openai_responses.rs` serializes only `input_text` and
ignores `msg.images` entirely. On the Responses provider the model answers as if
no image were attached — no error, no marker, no log — so a vision workflow that
works on one provider silently degrades to text-only on another.

## Outcome and validation

**Resolved on 2026-08-19.** The Responses provider serializes image
attachments. The user-message branch in `src/llm/openai_responses.rs` now emits
the text as `input_text` followed by one `input_image` content part per
attachment, carrying a `data:<mime>;base64,<data>` URI — matching the behavior
the Anthropic and Chat Completions providers already had.

Regression coverage asserts that an image-bearing turn produces an `input_image`
part with the expected data URI, and that a text-only turn still produces
exactly one `input_text` part (no empty image parts introduced).

Validation: `cargo test --all-targets` (55 binaries, 0 failures), clippy clean.

Boundary: image bytes are still bounded and SSRF-validated upstream by
`src/llm/image.rs`; this change only stops the provider from discarding them.
