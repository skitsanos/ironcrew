# IC-012 — Accidental off-main release tags lacked a guard

## Outcome and validation

**Resolved on 2026-08-07 for accidental/operator error.** The tag-triggered
workflow now runs a fail-closed
`guard` job before the platform build matrix. It checks out full history,
fetches `origin/main`, and calls `scripts/verify_release_source.sh` to require
both an exact `vX.Y.Z`/`Cargo.toml` match and a tag commit reachable from the
release branch. Every binary build declares `needs: guard`, so an off-main or
version-drifted tag cannot produce signed release artifacts.

The verifier is independently executable and fails on a missing tag, manifest,
release ref, version mismatch, or ancestry mismatch. Repository-policy tests
construct a temporary Git history and prove a valid main tag passes, an
unreviewed feature-branch tag fails, and a main tag checked out against a
different manifest version fails. The tests also parse CI YAML structurally and
require the build dependency.

Both repository-local release skills now describe only the intended branch/tag
contract and remove destructive reset and broad implicit staging advice. The
Bun policy/registry tests passed, all three workflows passed `actionlint`, and
Bun/yq parsed the workflows successfully.

GitHub loads a tag-push workflow from the tagged commit. An adversarial off-main
commit could modify or remove this guard before its tag is pushed, so the
in-repository check is not a security boundary against a release-capable actor.
IC-014 tracks tag rules, protected environments, or another trusted
default-branch control plane. This gate remains useful for normal operator
error; it does not replace branch protection, code review, artifact signatures,
or release monitoring.
