# IC-029 — Blocking filesystem and parse work runs on Tokio workers in several paths

## Finding

AGENTS.md requires Tokio workers to stay free of blocking filesystem, parsing,
and database work. `SqliteStore` follows this (every operation wraps
`spawn_blocking`, `src/engine/sqlite_store.rs`), but several sibling paths run
blocking work inline on the async executor:

- `JsonFileStore` (the default backend, used by the HTTP server) takes a
  process-wide `std::Mutex` and then performs synchronous reads up to 64 MiB and
  atomic writes with two `sync_all` fsyncs — directly in async `StateStore`
  methods (`src/engine/run_history.rs`). `MemoryStore::save()`
  (`src/engine/memory.rs`, called from `run_crew`) fsyncs synchronously, and
  `MemoryStore::persistent_with_config` (`src/lua/api.rs`) synchronously reads and
  parses up to 64 MiB. Under concurrent HTTP runs, heartbeat loops and run writes
  serialize on the mutex while worker threads park on disk syncs.
- The flow-inspection GET handlers `validate_flow` and `list_agents`
  (`src/api/handlers.rs`) build a full Lua VM and walk the project tree inline;
  as GETs they receive no admission class, so concurrency is unbounded and can
  starve the worker pool that also serves `/health`. `current_flow_source_snapshot`
  (`src/api/conversations.rs`) already wraps the equivalent walk in
  `spawn_blocking`.
- `web_scrape` runs `Html::parse_document` plus full-text extraction (up to 2 MiB)
  inline (`src/tools/web_scrape.rs`), while `template_render`, `validate_schema`,
  and the file tools correctly use `spawn_blocking`.

## Required outcome and acceptance

Blocking filesystem, fsync, and large-parse work must not run on Tokio worker
threads. Route JSON-store operations and memory save/load through blocking
workers, wrap the flow-inspection loader construction/parsing in `spawn_blocking`
(and give inspection GETs an admission class or a dedicated semaphore), and wrap
`web_scrape` parsing/extraction in `spawn_blocking`. Add or extend coverage
demonstrating the store and inspection paths no longer block the runtime (for
example, that a large JSON-store record does not stall concurrent requests), and
confirm the all-target Rust gates stay green.

## Outcome and validation

**Resolved on 2026-08-19.** The default JSON store now exposes an asynchronous
adapter whose complete `StateStore` implementation transfers each synchronous
core operation—including lock acquisition, bounded reads/JSON parsing, atomic
writes, and fsyncs—to `spawn_blocking`. Production construction uses the same
boundary. The mature synchronous core remains private and unchanged, while
focused adapter/core-operation modules keep the responsibility split explicit.
A deterministic current-thread regression holds the JSON run lock on one
blocking worker and proves a Tokio timer continues advancing while a store save
waits on another worker. SQLite directory creation, connection opening, and
migration initialization now also cross a blocking worker during async store
bootstrap; its individual operations already used that boundary.

Persistent crew-memory snapshot loading and atomic save/fsync now run on
blocking workers. `Crew.new` is registered as an async Lua function so
persistent memory can load without parking the executor, while the synchronous
constructor remains available for non-async embedding and tests.

The flow validation and agent-list handlers acquire a dedicated, process-local
inspection semaphore (`IRONCREW_MAX_ACTIVE_INSPECTIONS`, default `4`, hard
ceiling `64`) and fail fast with `503` when it is full. Project discovery, file
reads, Lua VM/parser construction, agent/tool definition parsing, HTTP run
runtime setup, `sql/*.sql` operation loading, and entrypoint reading all execute
inside blocking workers. The routes also use the independently bounded
observation admission class. `web_scrape` still caps the streamed HTML before
allocation, then performs DOM parsing and visible-text extraction on a blocking
worker.

Coverage pins JSON-lock/runtime progress, persistent-memory round trips,
inspection saturation, route classification, HTML extraction, and the existing
HTTP runtime source-snapshot contract. Validation passed: `cargo fmt --all
-- --check`; exact `cargo clippy --all-targets -- -D warnings`; `cargo test
--all-targets` (all local targets, zero failures); and the module-size policy
(204 production modules, 48/48 reviewed legacy exceptions). PostgreSQL behavior
and schema were not changed; the local PostgreSQL-gated binaries compiled but
their live database cases remained environment-gated for CI.

### Pre-implementation status note — 2026-08-19

At that checkpoint this was not yet implemented and was deliberately deferred
from the initial 2026-08-19 remediation pass.
This is the largest remaining item: it touches the default JSON store, memory
save/load, the two flow-inspection handlers, and `web_scrape`, and the store
changes in particular need care around the process-wide lock and the
owned-blocking-worker contract described in `AGENTS.md`. Doing it alongside the
security fixes in that pass would have made the change set hard to review.

### Closed inventory addition — 2026-08-19 (postgres-app-data branch)

`read_sql_dir` (`src/engine/app_db/operations/mod.rs`) performs synchronous
directory and file reads and is reached from the async HTTP run path via
`setup_crew_runtime_inner`. It is now covered by the HTTP runtime's single
blocking setup boundary, together with entrypoint discovery and reading.
