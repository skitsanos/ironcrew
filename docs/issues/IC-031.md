# IC-031 — Store failures are reported as 404 on run read and delete

## Finding

`get_run` and `delete_run` (`src/api/handlers.rs`) map every store error to
`404 Not Found` with the backend's raw error string as the body, for example
`state.store.get_run(&id).await.map_err(|e| error_response(StatusCode::NOT_FOUND,
e.to_string()))`. A transient store outage — a PostgreSQL failure or pool
exhaustion — is therefore indistinguishable from a genuinely missing run.

Concrete failure: a client polling `GET /flows/{flow}/runs/{id}` for a keyed
run's outcome sees 404 during an outage, concludes the run never existed or was
pruned, and per the documented idempotency contract may mint a new
`Idempotency-Key` and re-execute paid provider work. The correct pattern already
exists in the same file: `durable_run_location` distinguishes the
run-not-found validation message from other errors and maps the rest to 503.

## Outcome and validation

**Resolved on 2026-08-19.** `get_run` and `delete_run` (`src/api/handlers.rs`)
route store errors through a new `run_lookup_error` helper: a genuinely missing
run returns `404` with a stable message, while any other backend failure is
logged in full and answered with `503` and a generic body. A transient outage is
therefore no longer indistinguishable from "this run never existed", so a client
polling a keyed run cannot conclude the record is gone and re-execute paid
provider work under a fresh idempotency key.

Validation: `cargo test --all-targets` (55 binaries, 0 failures) including
`api_safety_test` (16 tests) and `http_audit_test`; clippy clean.

Boundary: flow scoping is unchanged — a run belonging to another flow still
reads as `404` rather than confirming it exists elsewhere.
