# IC-014 — Release publication lacks a platform-enforced trusted control plane

## Outcome and validation

**Resolved on 2026-08-12.** The closure combines the trusted-default-branch
request controller, active GitHub branch/tag/environment controls, future
immutable releases, environment-scoped Docker credentials, protected
`develop` to `main` integration, and two non-publishing live validation
canaries. The result is intentionally bounded to the accepted sole-owner
model: `skitsanos` is the trusted root and only current integration and release
approver; malicious or compromised owner authority remains out of scope.

### Original finding and acceptance

The repository now rejects ordinary off-main release tags from the checked-in
workflow, but GitHub evaluates a tag-push workflow from the tagged commit. A
release-capable actor can therefore tag an off-main commit that changes the
workflow itself and bypasses its ancestry guard. Repository shell logic alone
cannot establish an adversarial trust boundary.

A read-only GitHub API inspection on 2026-08-07 returned no repository
rulesets, no environments, and no protection object for `main` (HTTP 404).
That dated platform snapshot confirms the required control plane is not merely
undocumented; it is currently absent. Re-check it before remediation because
repository settings can change independently of this source tree.

Required outcome:

- configure protected `v*` tag rules and restrict tag creation to the release
  role, or move publication behind a trusted default-branch/manual control plane;
- require a protected release environment with an explicit approval gate for
  contents-write and OIDC-signing jobs;
- keep guard/build jobs at `contents: read` and grant write/OIDC only to the
  final publication job;
- verify tag ancestry, annotated-tag type, manifest version, reviewed commit,
  and exact workflow identity before publication;
- document who can approve, tag, dispatch, rerun, and bypass the environment,
  including the accepted owner-compromise boundary; and
- capture non-secret GitHub ruleset/environment evidence plus one denied
  off-main/adversarial canary and one successful main release dry run.

This issue concerns release authority, not the cryptographic validity of an
artifact produced after a legitimately authorized release.

## Local trusted-control checkpoint — 2026-08-12

Current source confirms the original finding. The former tag-push release
workflow was selected from the tagged commit, so its ancestry shell guard could
not be an adversarial trust boundary. The local checkpoint removes that trigger
and admits release and Docker-promotion requests only through two versioned
`repository_dispatch` event types. GitHub selects those workflows from the
default branch (`main`), independently of the requested release tag:

- `ironcrew_release_v1` selects `.github/workflows/release.yml`;
- `ironcrew_docker_publish_v1` selects
  `.github/workflows/docker-publish.yml`; and
- both accept a `client_payload` containing exactly `tag` and `mode`, where the
  tag is an exact stable `vX.Y.Z` tag and the mode is `validate` or `publish`.

The guard jobs bind the event, repository, default branch, sender, workflow
reference, workflow SHA, and trusted-control checkout before consuming the
payload. Release source is checked out separately. The release tag must be an
annotated tag that points directly to a commit, its manifest version must match,
and that exact commit must be reachable from `main`. Builds use the resolved
commit SHA. Before publication, the final job re-fetches and revalidates the
tag-to-commit and source-time binding while continuing to run the workflow and
verification scripts from trusted `main`. The signed artifact identity is now
the exact `release.yml@refs/heads/main` workflow identity; the signed receipt
continues to bind the release tag and commit.

Both workflows include a non-publishing `validate` mode. It reaches a job named
for the `release` environment with `contents: read`, but cannot create a GitHub
release, request an OIDC signing token, read Docker credentials, or modify a
registry. Publish mode keeps source/build/package work in contents-read jobs;
the final environment-gated release job only independently verifies the exact
expected artifact set, signs it, and creates the release once. Docker
credentials are referenced only by the environment-gated promotion job. These
repository controls are defense in depth until the remote environment and
repository policy exist.

### Read-only platform revalidation

A second read-only GitHub API inspection on 2026-08-12, before the live
remediation below, found:

- zero repository rulesets, zero environments, and no `main` protection object
  (the protection endpoint returned `404`);
- one direct collaborator, repository owner `skitsanos`, with administrator
  access, so no independent release approver currently exists;
- Actions enabled with all actions allowed, default workflow permissions set to
  read, pull-request approval by workflows disabled, and full-SHA action pinning
  not required;
- `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` still stored as repository-scoped
  Actions secrets rather than protected `release`-environment secrets; and
- GitHub immutable releases disabled (`enabled: false`,
  `enforced_by_owner: false`).

The newly previewed Actions workflow-execution-policy control was not treated
as evidence because its state was not authoritatively available through the
stable API inspection. In the original multi-actor threat model that was a
material residual: default-branch
`repository_dispatch` prevents this workflow from selecting an off-main
revision, but a tag-capable actor could add a different tag-push workflow to an
off-main commit and tag it. That analysis is superseded below by the accepted
sole-owner model: only the trusted owner may create `v*` tags, and compromised
owner authority is out of scope. The current CI still legitimately uses `push`
on `main` and `develop`, so a broad preview policy is not introduced without a
separate design and canary.

Dispatch itself is not a least-privilege approval channel. GitHub requires a
fine-grained token with repository Contents write to create a
`repository_dispatch`, so a holder is already repository-write-capable outside
the protected environment. Matching the event sender to `github.actor` is a
consistency check, not a release-operator allowlist. The accepted model
therefore uses the lower-authority Issues request channel implemented below
instead of a standing dispatch credential.

Finally, tag revalidation and `gh release create --verify-tag` are separate
operations. Without active tag rules, a tag-capable actor can move, delete, or
recreate `v*` between them. Closure requires active `v*` rules restricting
creation and preventing update/deletion without an administrator bypass, plus
immutable GitHub releases, so the exact annotated tag remains stable through
publication.

### Accepted sole-owner authority model — 2026-08-12

The repository owner confirmed that `skitsanos` is currently the only person
who approves `develop` to `main` integration and releases. IC-014 therefore no
longer requires a second human reviewer that does not exist. The accepted
control model treats that sole owner as the trusted root: the same identity may
request, approve, and rerun a release, while branch, tag, environment, immutable
release, and workflow controls prevent accidental or out-of-band publication.
A malicious or compromised repository owner remains outside the claimed threat
model because that identity can ultimately change repository settings and
trusted `main` itself.

The least-standing-authority request path is an owner-authored issue with the
exact `release-request` label and a canonical bounded JSON body. A trusted
default-branch controller validates the repository, owner, actor, issue
metadata, target, stable tag, and `validate` or `publish` mode, then uses only
its run-scoped `GITHUB_TOKEN` to create the fixed downstream
`repository_dispatch`. No long-lived Contents-write personal token is required.
The protected `release` environment still requires an explicit deployment
approval, but self-approval is intentional in this model; publication never
follows merely from merging or tagging.

Each application of the exact label and each owner-triggered rerun is a
deliberate new authorization. The controller serializes attempts per issue but
does not claim one-shot deduplication; the downstream release and promotion
protocols remain fail-closed under replay. The owner closes the request issue
after its downstream run finishes.

### Live platform-control outcome — 2026-08-12

GitHub immutable releases are now enabled for this repository. The API reports
`enabled: true` and `enforced_by_owner: false`. This protects future releases;
it did not retroactively make the existing `v2.22.0` release immutable, whose
API record still reports `immutable: false`.

At the interim checkpoint, active repository tag ruleset `20741649`, named
`Lock v* release tags pending trusted publisher`, targeted `refs/tags/v*` and
restricted tag creation, update, and deletion. It had no bypass actors, and the
API reported that the current user could never bypass it. This was deliberately
a fail-closed interim policy before the final owner-only creation rule was
installed.

A real push canary attempted to create
`v0.0.0-ic014-lock-canary-20260812`. GitHub rejected it with `GH013` under the
repository rules, and a follow-up ref lookup confirmed that the tag does not
exist remotely. This supplies the required denied tag-control canary without
creating a release or publishing an image.

The sole-owner controls were then applied without opening a publication path:

- protected environment `release` (`19770322300`) requires an explicit review
  by `skitsanos`, permits that deliberate self-review, disables administrator
  bypass in the authenticated UI, and admits only `main` through branch policy
  `57181717`;
- active no-bypass branch ruleset `20762614` requires a pull request, resolved
  conversations, a current head, and the nine established CI jobs on `main`,
  with zero second-person approvals under the accepted model, while blocking
  deletion and non-fast-forward updates;
- active tag-creation ruleset `20762625` allows only user `skitsanos` to bypass
  the `v*` creation restriction, while ruleset `20741649` has no bypass and
  prevents every actor, including the owner, from moving or deleting `v*`;
- exact label `release-request` now identifies owner requests; and
- `DOCKERHUB_USERNAME` and a new 90-day read/write Docker Hub token are scoped
  only to the `release` environment. The repository-level secrets are empty,
  and the positively attributed legacy token `ironcrew-git-publish` was
  deleted.

The first replacement token generated during migration appeared in the
automation transcript and was therefore treated as compromised. It was revoked
before use or GitHub storage. A separately generated replacement was transferred
without rendering or retaining its value. No release, release tag, image,
registry alias, or publication dispatch was created by these controls.

### Protected integration and live validation — 2026-08-12

The trusted controls reached `main` through protected pull request
[#63](https://github.com/skitsanos/ironcrew/pull/63). Its exact head
`bd829415dff114c5cfc7faafb5a72d15c4b7f755` passed all nine required jobs in
[PR CI run 31633359970](https://github.com/skitsanos/ironcrew/actions/runs/31633359970),
then merged as `0ece62c4973d343b83f8ea8d31a28a7bc7cb043c`. The resulting exact `main`
commit passed the same nine jobs in
[main CI run 31634085607](https://github.com/skitsanos/ironcrew/actions/runs/31634085607),
including PostgreSQL integration, the replica-soak smoke, Windows compilation,
macOS tests, repository policy, dependency audit, Lua examples, crew contract,
exact Clippy, all-target tests, and the release build.

Two owner-authored, exact-body issues exercised the lower-standing-authority
request path against that `main` commit:

- closed issue [#64](https://github.com/skitsanos/ironcrew/issues/64) requested
  `{"target":"release","tag":"v2.22.0","mode":"validate"}`. Controller
  [run 31635027122](https://github.com/skitsanos/ironcrew/actions/runs/31635027122)
  validated the issue and dispatched only the release event. Downstream
  [run 31635064079](https://github.com/skitsanos/ironcrew/actions/runs/31635064079)
  passed the trusted-main guard and the owner-approved protected validation
  job. The target-matrix build, immutable-image build, and `Create Release`
  jobs were all skipped, and the run created zero Actions artifacts.
- closed issue [#65](https://github.com/skitsanos/ironcrew/issues/65) requested
  `{"target":"docker","tag":"v2.22.0","mode":"validate"}`. Controller
  [run 31635324542](https://github.com/skitsanos/ironcrew/actions/runs/31635324542)
  validated the issue and dispatched only the Docker event. Downstream
  [run 31635348636](https://github.com/skitsanos/ironcrew/actions/runs/31635348636)
  passed the trusted-main guard and the owner-approved protected validation
  job. `Promote signed release image` was skipped, and the run created zero
  Actions artifacts.

Both approvals were normal approvals by `skitsanos` for protected environment
`release` (`19770322300`), not administrator bypasses. The final remote policy
set remained branch ruleset `20762614`, owner-only tag-creation ruleset
`20762625`, no-bypass tag-update/deletion ruleset `20741649`, and main-only
environment branch policy `57181717`.

Before and after each canary, the normalized snapshot covered the exact `main`
ref, all `v*` refs, GitHub release records and assets, and every public
`skitsanos/ironcrew` Docker tag. All four snapshots had SHA-256
`0ec913fd66f5bfc4bfee560d5d4100f3edd6d50368e406898b09f7e4c357aa31`.
Consequently neither canary created or changed a release, tag, release asset,
image, or registry alias. They also left `main` at the already reviewed
`2.24.0` product version; no additional product-version change occurred.

This closes the authority and dry-run acceptance boundary without exercising
publish mode. A future release still requires separate authorization, a product
version bump in `Cargo.toml` and the root `Cargo.lock`, a matching annotated Git
tag, and the protected publish path. The repository's preview Actions Policies
page still has no policies; under the accepted sole-owner model that remains
optional defense in depth rather than a closure requirement, because it cannot
protect against the trusted owner and a broad event restriction would disrupt
current CI and the request controller.
