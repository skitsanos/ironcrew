# IC-014 — Release publication lacks a platform-enforced trusted control plane

## Required outcome and acceptance

The repository now rejects ordinary off-main release tags from the checked-in
workflow, but GitHub evaluates a tag-push workflow from the tagged commit. A
release-capable actor can therefore tag an off-main commit that changes the
workflow itself and bypasses its ancestry guard. Repository shell logic alone
cannot establish an adversarial trust boundary.

A read-only GitHub API inspection on 2026-08-07 returned no repository
rulesets, no environments, and no protection object for `main` (HTTP 404).
That dated platform snapshot confirms the required control plane is not merely
undocumented; it is currently absent. Re-check it before remediation because
repository settings can change independently of this source tree.

Required outcome:

- configure protected `v*` tag rules and restrict tag creation to the release
  role, or move publication behind a trusted default-branch/manual control plane;
- require a protected release environment with independent approval for
  contents-write and OIDC-signing jobs;
- keep guard/build jobs at `contents: read` and grant write/OIDC only to the
  final publication job;
- verify tag ancestry, annotated-tag type, manifest version, reviewed commit,
  and exact workflow identity before publication;
- document who can approve, tag, dispatch, rerun, and bypass the environment; and
- capture non-secret GitHub ruleset/environment evidence plus one denied
  off-main/adversarial canary and one successful main release dry run.

This issue concerns release authority, not the cryptographic validity of an
artifact produced after a legitimately authorized release.

## Local trusted-control checkpoint — 2026-08-12

Current source confirms the original finding. The former tag-push release
workflow was selected from the tagged commit, so its ancestry shell guard could
not be an adversarial trust boundary. The local checkpoint removes that trigger
and admits release and Docker-promotion requests only through two versioned
`repository_dispatch` event types. GitHub selects those workflows from the
default branch (`main`), independently of the requested release tag:

- `ironcrew_release_v1` selects `.github/workflows/release.yml`;
- `ironcrew_docker_publish_v1` selects
  `.github/workflows/docker-publish.yml`; and
- both accept a `client_payload` containing exactly `tag` and `mode`, where the
  tag is an exact stable `vX.Y.Z` tag and the mode is `validate` or `publish`.

The guard jobs bind the event, repository, default branch, sender, workflow
reference, workflow SHA, and trusted-control checkout before consuming the
payload. Release source is checked out separately. The release tag must be an
annotated tag that points directly to a commit, its manifest version must match,
and that exact commit must be reachable from `main`. Builds use the resolved
commit SHA. Before publication, the final job re-fetches and revalidates the
tag-to-commit and source-time binding while continuing to run the workflow and
verification scripts from trusted `main`. The signed artifact identity is now
the exact `release.yml@refs/heads/main` workflow identity; the signed receipt
continues to bind the release tag and commit.

Both workflows include a non-publishing `validate` mode. It reaches a job named
for the `release` environment with `contents: read`, but cannot create a GitHub
release, request an OIDC signing token, read Docker credentials, or modify a
registry. Publish mode keeps source/build/package work in contents-read jobs;
the final environment-gated release job only independently verifies the exact
expected artifact set, signs it, and creates the release once. Docker
credentials are referenced only by the environment-gated promotion job. These
repository controls are defense in depth until the remote environment and
repository policy exist.

### Read-only platform revalidation

A second read-only GitHub API inspection on 2026-08-12 found:

- zero repository rulesets, zero environments, and no `main` protection object
  (the protection endpoint returned `404`);
- one direct collaborator, repository owner `skitsanos`, with administrator
  access, so no independent release approver currently exists;
- Actions enabled with all actions allowed, default workflow permissions set to
  read, pull-request approval by workflows disabled, and full-SHA action pinning
  not required;
- `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` still stored as repository-scoped
  Actions secrets rather than protected `release`-environment secrets; and
- GitHub immutable releases disabled (`enabled: false`,
  `enforced_by_owner: false`).

The newly previewed Actions workflow-execution-policy control was not treated
as evidence because its state was not authoritatively available through the
stable API inspection. That is a material residual: default-branch
`repository_dispatch` prevents this workflow from selecting an off-main
revision, but a tag-capable actor could add a different tag-push workflow to an
off-main commit and tag it. Platform workflow-execution protections must reject
untrusted actors/events, or a dedicated release authority must provide an
equivalent boundary. The current CI still legitimately uses `push` on `main`
and `develop`, so globally denying push-triggered workflows would require an
agreed CI-trigger migration rather than an ad hoc release setting.

Dispatch itself is not a least-privilege approval channel. GitHub requires a
fine-grained token with repository Contents write to create a
`repository_dispatch`, so a holder is already repository-write-capable outside
the protected environment. Matching the event sender to `github.actor` is a
consistency check, not a release-operator allowlist. Closure therefore also
requires either a dedicated constrained release App/authority or a lower-
authority request channel (for example, an Issues-only request that a trusted
controller validates) plus the platform actor/event controls.

Finally, tag revalidation and `gh release create --verify-tag` are separate
operations. Without active tag rules, a tag-capable actor can move, delete, or
recreate `v*` between them. Closure requires active `v*` rules restricting
creation and preventing update/deletion without an administrator bypass, plus
immutable GitHub releases, so the exact annotated tag remains stable through
publication.

No environment, ruleset, branch protection, collaborator, secret scope,
immutable-release setting, tag, workflow run, release, or registry state was
changed. In particular, neither the denied adversarial canary nor the successful
protected-main dry run has been executed.

IC-014 therefore remains `in-progress`. Before either dispatch event is used,
the repository still needs a protected `release` environment, the Docker Hub
secrets moved into that environment, active immutable `v*` and GitHub-release
controls, a dedicated constrained request authority, a documented independent
reviewer and bypass policy, and default-branch plus workflow-execution controls
that prevent unreviewed workflows from running. With only the sole owner
available, the required independent approval cannot yet be satisfied. Remote
evidence must then capture the non-secret configuration, one denied adversarial
request, and one successful `validate` request without publication. Publish mode
remains prohibited until those controls and evidence exist.
