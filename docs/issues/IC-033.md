# IC-033 — Provider request timeout is a fixed 120s total deadline

## Finding

All three providers build their reqwest client with `timeout(120s)`
(`src/llm/anthropic.rs`, `src/llm/openai.rs`, `src/llm/openai_responses.rs`). In
reqwest this is a total deadline covering the full body/stream read, not just
connect. An extended-thinking response (the thinking budget can legally reach tens
of thousands of tokens per `MAX_THINKING_BUDGET`) or a long tool-loop generation
routinely exceeds 120 s, so the stream is aborted mid-flight and the request fails
with "stream ended before message_stop" — and can never succeed, because there is
no operator override. Every byte limit, by contrast, is configurable through
`ProviderExecutionPolicy` (`src/llm/execution_policy.rs`).

## Required outcome and acceptance

Long but legitimate provider responses must be able to complete. Split the fixed
deadline into a connect timeout plus a configurable total (or idle) timeout
captured in the execution policy so it participates in the durable-conversation
fingerprint, with a sane default that does not truncate normal extended-thinking
responses. Add coverage asserting the timeout is policy-driven (for example,
that an overridden value is reflected in the constructed client configuration).

### Status note — 2026-08-19

Not yet implemented. Deliberately deferred from the 2026-08-19 remediation pass:
the fix belongs with the shared provider scaffolding in [IC-037](./IC-037.md),
because the 120-second client deadline is duplicated across all three providers
and should be made policy-driven once, not three times. The duplication itself
is recorded in IC-037; this issue tracks the timeout contract.
