# IC-017 — Durable SSE edge cases lack a separate-process gate

## Outcome and validation

**Resolved locally on 2026-08-08.** The separate-process PostgreSQL target
previously proved retained cursor resume and terminal replay through a peer,
while malformed, cross-run, ahead-of-journal, pruned-cursor, explicit-gap, and
incomplete-terminal behavior remained below the process boundary.

The extended gate starts two real IronCrew processes against disposable
PostgreSQL 15.18. Replica A owns a provider-free run while non-owner replica B
serves the event stream and all cursor probes. The gate covers missing
authentication, malformed and non-ASCII values, zero and non-canonical
sequences, cross-run cursors, cursors ahead of the journal, and physically
expired cursors with exact HTTP status and body assertions. Success and failure
paths also assert the documented content type, cache policy, buffering header,
and authentication-first behavior.

A four-event per-run limit and 1 KiB event/page limits force deterministic
capacity eviction. The test records all seven original payloads, retained
bounds, byte usage, row counts, one explicit writer-backpressure gap, boundary
resume without duplicates, and then retention through the terminal sequence.
After retention, repeated reads return the same unnumbered incomplete terminal
fallback and bounded maintenance reduces journal usage to zero. A row-scoped
database barrier separately proves the 100 ms read deadline, exact non-cacheable
`503`, bounded live-stream closure after repeated timeouts, readiness confirmed
after lock release, and successful replay from a fresh request.

The gate scans every journal payload and error body for HITL prompts, choices,
answers, API tokens, idempotency material, and encryption-key material. Four
consecutive focused runs passed in 7.69, 7.76, 7.71, and 7.68 seconds. The final
complete separate-process target passed 5/5, and the complete PostgreSQL target
set passed 2/2 multi-replica HTTP tests, 44/44 store tests, and 5/5 process
tests. Schema, function, and replica-backend cleanup was verified before the
disposable database was removed.

This resolves the local process-boundary gate. At this issue's resolution,
Railway/OpenShift load-balancer routing was still assigned to IC-007; IC-007's
later deployed canaries closed that platform boundary. This page remains the
authoritative local-process receipt rather than duplicating the platform proof.

## Post-resolution CI stabilization — 2026-08-19

Two current-tree dependency PR runs exposed a narrow observation race in this
acceptance harness. Run 32281815987 attempt 1 received the documented journal
read-timeout `503` before the bounded terminal replay, and run 32283293777
received the same response before its resumed replay. Both failures occurred
after the 2/2 multi-replica and 48/48 PostgreSQL store suites passed; the same
Rust tree passed on the corresponding `develop` and rerun receipts.

Successful SSE probes now retry only the exact non-cacheable
`{"error":"Run-event replay is temporarily unavailable"}` response. The loop
is capped at five attempts with bounded backoff; any other status or body still
fails immediately, and the existing payload-secret scan runs before any retry.
Production replay, timeout, readiness, and persistence behavior is unchanged.

Against a freshly pulled disposable PostgreSQL 15 container, the focused real
two-process IC-017 scenario passed 5/5 repetitions in 19.50–20.29 seconds. The
new classifier regression also proves that a success status or a different
`503` body is never accepted as this retryable condition. IC-017 therefore
remains resolved; this is a harness stabilization rather than a weakened replay
contract or a new product finding.

## Post-timeout reconnect stabilization — 2026-10-21

PR #134's [CI run 39611176394](https://github.com/skitsanos/ironcrew/actions/runs/39611176394)
failed on PostgreSQL 18.6 when the post-timeout reconnect returned `503` instead
of the probe's expected `200`. This recovery request still bypassed the bounded
journal-unavailability retry used by the other successful SSE probes. Readiness
checks storage health separately; a ready response does not guarantee that a
particular run's journal read completes within the deliberately short 100 ms
deadline. The failed assertion captured the status rather than the response
body, so it does not establish a dependency regression or a specific store error.

Recovery now uses the existing five-attempt helper. Only the exact journal
unavailability body, with the required non-cacheable header and payload-secret
scan, permits another attempt. The lock-held initial `503`, five live-read
deadlines, error frame, stream closure, recovered event ID, and redaction checks
remain enforced. No runtime timeout or production behavior changed.

Three deterministic loopback HTTP regressions prove recovery on the fifth
attempt with authentication and cursor preserved, failure after five transient
responses, and immediate failure for another `503` body. The real two-process
IC-017 scenario passed five consecutive repetitions on each freshly pulled
disposable image: PostgreSQL 17.11 (`sha256:a63c1ea3f6a3a5a1621f97d2aba3b30faecfab4224c1b0000cc85ced57bb1939`)
in 17.41–19.00 seconds and PostgreSQL 18.6
(`sha256:1267c7e692de235fda2a50dbcdbcbca4672ea6a0298576a6bd9d07cafc319b32`)
in 17.49–20.87 seconds. The focused command was
`cargo test --locked --all-features --test two_process_replica_acceptance_test phase2::ic017::ic017_durable_sse_edges_cross_real_process_boundary -- --exact --test-threads=1`,
with each disposable URL supplied explicitly through `IRONCREW_TEST_PG_URL`.
Formatting, all-target Clippy with warnings denied, and all-target tests also
passed. IC-017 remains resolved; this receipt covers the local acceptance
harness, not new deployed or live-provider evidence.
