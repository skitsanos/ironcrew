# IC-020 — Cluster-wide admission and drain lifecycle lack acceptance

## Outcome and validation

**Resolved on 2026-08-10.** IronCrew now treats active-run, conversation, SSE,
Lua/task/provider concurrency, database-pool, and request-bucket limits as
process-local capacity. PostgreSQL idempotency and journal limits remain one
shared durable budget. A customer-wide request or provider quota is not
advertised as an IronCrew process limit and belongs at a trusted gateway or the
provider. This avoids a misleading cluster-global claim and a PostgreSQL hot
row for ordinary request admission.

The process lifecycle is monotonic: `accepting -> fencing -> draining ->
stopping`. Unix `SIGUSR1` performs an explicit drain without exiting;
`SIGTERM` and Ctrl+C use the same durable fence before stopping. Readiness drops
at `fencing`, while authenticated reads, run SSE, capabilities, and metrics
remain observable. Mutations received by the draining process return
non-cacheable `503 instance_draining`. PostgreSQL marks each owned in-flight
keyed-run ledger under the global run fence, so a peer cancellation or HITL
answer returns `503 run_owner_draining` without mutating control state. Fence
failure keeps the process unready and retries with bounded database operations
instead of entering `stopping` and falsely acknowledging peer control.

Fixed-cardinality protected metrics now expose lifecycle state/rejections,
Linux process RSS/high-water availability, this process's SQLx pool
open/in-use/limit, logical provider futures current/peak, SSE current/limit, and
registered EventBus instances, retained events/approximate serialized bytes,
and summed capacities. Provider guards release on completion, error, or
cancellation. A terminal run monitor releases its extra EventBus owner before
late-SSE retention; regressions prove late replay remains available while
successive fast runs stay within the configured buffer count and eventually
return every EventBus gauge to zero.

The local PostgreSQL lifecycle gate passed 2/2 in 6.21 seconds with real
processes, explicit drain, a blocked durable-fence retry, peer control
rejection, exactly one terminal transition, stable replay, and replacement.
The separate release-binary resource gate then saturated one, two, and three
processes. At `R=1/2/3`, PostgreSQL connections and provider peaks were exactly
`2/4/6`, SSE streams were `2/4/6` with one extra rejection per process,
EventBus retained bytes were `632/1,264/1,896`, and aggregate host RSS was
`17,694,720/35,946,496/54,280,192` bytes against a 256 MiB-per-process
comparator. All active/EventBus gauges reached zero within 957 ms after each
phase. The reviewed receipts are under
`evaluations/replica-lifecycle/reports/`.

### Railway canary

The temporary sandbox scaled `1 -> 2 -> 1`. Thirty routed probes observed and
mapped both `X-IronCrew-Instance-Id` values to exact runtime Railway replica
IDs. A held owner entered explicit drain; direct mutations returned
`instance_draining`, peer answer/abort returned `run_owner_draining`, and reads
remained available. Railway continued routing some requests to the drained
process, proving the application fence rather than ingress withdrawal is the
safety boundary. `SIGTERM` spent approximately five seconds in routing grace,
persisted one `Aborted` terminal event, and restarted in place under the same
Railway replica ID. Same-key replay retained the original run/owner, and the
restarted process completed a second peer-answered HITL run successfully.

At two replicas, `/proc` RSS totaled about 27.25 MiB, each SQLx pool reported
two open connections, and PostgreSQL observed four idle application sessions,
against the declared aggregate limit of 2 vCPU and 2,000,000,000 bytes. Railway
platform memory telemetry was materially lower than `/proc` RSS and is not
treated as sizing truth. The timing configuration `5 + 15 + 1` seconds fit the
30-second platform drain budget.

### OpenShift canary and readiness correction

The restricted-v2 canary first exposed a real rolling-availability defect:
overlapping kubelet/operator readiness probes could lose a `try_lock` race and
return a contention-only `503` after a replacement first became Ready. The
handler now coalesces probes behind the in-flight health check for up to one
second and still fails closed if that check stalls. The rolling contract also
requires a measured non-zero `minReadySeconds` stabilization window.

Both corrected replicas passed 64/64 parallel direct readiness requests. With
`minReadySeconds: 10`, `maxUnavailable: 0`, and `maxSurge: 1`, the final
homogeneous rollout kept two to three physical pods and two to three Ready
pods. Direct stable-peer readiness/capabilities passed 60/60 each, and the
affinity-free shared Route passed 60/60 readiness, 60/60 liveness, and 60/60
capability requests across both identities. There were zero
`readiness_check` failures. The retiring deployment-specific route truthfully
returned one lifecycle `503` and one timeout while its old endpoint
disappeared; the shared route remained continuous.

The same platform gate proved `1 -> 2 -> 1` sessions/routing, real `SIGUSR1`
EndpointSlice withdrawal in 3.201 seconds, direct and peer drain rejection,
real PID 1 `SIGTERM` exit code zero, exactly one durable `Aborted` terminal
event, an empty mailbox, and stable same-key replay. Final app pods ran as
arbitrary UID `1004800000` under `restricted-v2`, with 500m/512 MiB limits,
about 15.3/14.5 MiB process RSS, and two PostgreSQL pool connections each.

The final live PostgreSQL matrix passed 2/2 multi-replica HTTP tests, 45/45
store tests, and 9/9 genuine two-process tests. Bounded Railway and OpenShift
log/database/report scans found none of the exact canary credentials or HITL
plaintext. Railway returned to zero active services/instances/volumes/buckets
(its deleted canary volume remains an asynchronous tombstone), while the
project/environment were preserved. OpenShift dropped every prefixed database
object, deleted exactly the 14 labeled canary objects, restored quota use to
zero, and matched the 25-object shared-namespace baseline byte-for-byte.

This resolves the bounded lifecycle, admission-ownership, resource, and
Railway/OpenShift rollout gate. It does not make live conversations portable,
provide execution takeover, make a deployment-specific direct route zero-gap,
establish a provider/customer-global quota, or replace IC-018's 30–60 minute
retention-boundary soak. IC-007's later closure supplied the broader
per-platform feature matrix and Railway staged-key/owner-death evidence.
IC-010 retains broader operational metric families.

### Post-resolution CI stabilization — 2026-08-12

Main CI run
[31636829823, attempt 2](https://github.com/skitsanos/ironcrew/actions/runs/31636829823/attempts/2)
reported `Abandoned` instead of `Aborted` in the IC-020 clean-drain process
gate. The merge commit and the immediately preceding green `develop` commit
had the identical Git tree; the same gate had passed in
[run 31636142854](https://github.com/skitsanos/ironcrew/actions/runs/31636142854).
The failure was a harness phase-alignment race at the intentionally exercised
six-second minimum lease: the injected global-fence delay could consume the
remaining lease interval before the clean-shutdown assertion began. A real
database-clock expiry must remain `Abandoned`, including after a drain marker,
so production reconciliation was not changed.

The process gate now observes a fresh database-backed lease immediately before
each termination boundary. During the deliberate global-fence contention it
accepts only the exact temporary `503 storage_maintenance` readiness state and
requires peer recovery. It also rejects the graceful-teardown timeout fallback
and reports the phase, run ID, and redacted child logs on a terminal mismatch.

The first stabilization passed the full `develop` and pull-request gates, but
exact-main [run 31641220110](https://github.com/skitsanos/ironcrew/actions/runs/31641220110)
then exposed a second measurement race: after direct `SIGTERM`, the routing-grace
clock can expire while the injected global fence is still blocked, so the owner
may commit its drain marker and close the listener before a later HTTP sample
can observe `draining`. The explicit `SIGUSR1` path still requires the live HTTP
`draining` and capabilities proof. The blocked `SIGTERM` path now retains its
pre-release HTTP `fencing` proof, then independently requires the exact durable
owner-drain marker, a bounded zero-status exit without the teardown fallback,
and eventual peer readiness before asserting the final `Aborted` state. It does
not accept `Abandoned` or change production reconciliation.

Against freshly pulled `postgres:15` image digest
`sha256:6eb0add3b77c081df18aa518ce43df58fdcc40f2e6d868a6fd08038dc7acd425`,
the final corrected IC-020 process scenario passed 10/10 repeated runs; the
complete serial local gate then passed 2/2 multi-replica HTTP, 48/48 PostgreSQL
store, and 12/12 two-process tests. This stabilizes the acceptance measurement
without changing IC-020's resolved product contract or owner-death semantics.

### Post-resolution shutdown race fix — 2026-08-19

A fresh full PostgreSQL process gate reproduced `Abandoned` once on the first
clean-drain phase even though the same focused scenario immediately passed.
The owner logs showed no terminalization before its clean process exit. The
cause was a production selection race in `serve_with_lifecycle`: after the
shutdown coordinator sent the stopping signal and closed the listener, both
the stopping receiver and server future could become ready together. The
unbiased selection could choose the server branch and abort the coordinator
while it was still waiting for active run terminal acknowledgements.

The stopping branch is now biased ahead of listener completion. Once stopping
has been signaled, the coordinator therefore retains ownership until bounded
teardown finishes, and active durable runs cannot be abandoned merely because
listener shutdown won the same scheduler turn. The change preserves real
owner-death reconciliation and the existing teardown watchdog.

On PostgreSQL 15.19, the corrected IC-020 scenario passed 5/5 repeated focused
runs and then passed inside the complete 13/13 genuine two-process suite. The
same disposable database also passed 4/4 application-data, 2/2 multi-replica
HTTP, and 48/48 store tests.
