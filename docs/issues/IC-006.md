# IC-006 — Unkeyed wrong-owner control lacks a separate-process gate

## Outcome and validation

**Resolved locally on 2026-08-07.** A new provider-free fixture runs one
conditionally skipped task before parking at process-local human input. This
ensures the unkeyed run is durable before B classifies ownership, while making
no model or tool request. A and B run as separate `ironcrew serve` processes
with required idempotency disabled only for this isolated pair.

B returned the exact structured `409 run_owned_by_another_instance`, named A,
reported `control_scope: "process"`, and recorded no false success. Run,
ledger, mailbox, and event state stayed unchanged; A retained the same local
question and renewed its lease. Both replicas returned the same stable run
history. Graceful `SIGTERM` of A then persisted `Aborted`, retained the one
successful skipped result, and appended exactly one durable `run_complete` at
the journal's terminal sequence. B stayed ready. A post-terminal abort through
B returned exact `404`, and the two abort audits were failed `409`/`404` rows
for the authenticated principal with zero successful abort audit.

The focused two-process PostgreSQL 15 gate passed 1/1 in 3.89 seconds. Exact
all-target Clippy passed. This proves diagnostic correctness only: unkeyed
control still requires owner routing, and Railway/OpenShift routing remains a
separate deployment gate.
