# IC-057 — Dependency audit fails because chrono is unmaintained

## Finding

Reproduced in hosted CI on 2026-11-20: after the lockfile refresh merged into
`develop`, `cargo audit --deny warnings` failed on one denied warning,
`RUSTSEC-2026-0543`, which reports `chrono` 0.4.45 as unmaintained. The
advisory names no vulnerability and has no patched version, so no lockfile
update clears it.

`chrono` was a direct dependency (`serde` feature only) and is also resolved
by `rmcp`. IronCrew used it in 26 production and 15 test files: for
`Utc::now().to_rfc3339()` timestamps, RFC 3339 parsing of stored values,
lease, retention and recovery-grace arithmetic, one microsecond canonical
form for PostgreSQL and one `NaiveDate` check of model snapshot dates. No
`chrono` type was serialized; every stored and returned timestamp is a
`String`.

## Interim exception

`.cargo/audit.toml` ignores `RUSTSEC-2026-0543` only, with the review, the
exposure and the exit condition recorded beside the entry. Validation on that
change: `cargo audit --deny warnings` passed with the exception and still
failed without it; the repository-policy tests and the issue registry check
passed.

## Required outcome and acceptance

Remove IronCrew's direct use of `chrono` (for example by moving timestamps to
`jiff` or `time`) while keeping every stored and returned timestamp
byte-identical, with parity tests for formatting and parsing of the existing
forms. Then remove the exception once no resolved crate depends on `chrono`,
or record the remaining upstream dependent and keep the exception narrowed to
it. Close when the audit passes without the exception, or when the remaining
transitive use is reviewed and documented with a new review date.

## Outcome and validation

### Migration

`chrono` is no longer an IronCrew dependency, and no crate replaces it. Every
instant is an `ironcrew::utils::timestamp::Timestamp`: whole seconds and
nanoseconds since the Unix epoch over `chrono`'s own range (the years -262143
to 262142), with the proleptic Gregorian conversions in a 42-line module.

`jiff` 1.0 was tried first, following the sibling IronFlow migration, and
rejected: its `Timestamp` ends at 9999-12-30T22:00:00.999999999Z. The live
PostgreSQL suite reproduced the consequence. Its far-future sentinel
`9999-12-31T23:59:59Z`, which `chrono` read, was refused as out of range, and
lease saturation to `chrono`'s maximum could not be represented. `time` has
the same default year range. A standard-library type keeps every previously
accepted input and every overflow result, and adds no dependency.

All text forms are produced and read in `src/utils/timestamp/`:

| form | example | used by |
| --- | --- | --- |
| `to_rfc3339` | `2026-01-02T03:04:05.120+00:00` | run, conversation, idempotency, HITL, journal and audit records on JSON, SQLite and PostgreSQL; API bodies; Lua `now_rfc3339()` |
| `to_rfc3339_micros_z` | `2026-01-02T03:04:05.120000Z` | PostgreSQL canonical timestamps |

`to_rfc3339` omits the fraction for a whole second and otherwise writes three,
six or nine digits, whichever is shortest without loss; years outside 0000 to
9999 carry a sign, as before. `parse_rfc3339` is a port of `chrono` 0.4.45's
`parse_from_rfc3339`: the same grammar (`T`, `t` or a space; any number of
fraction digits, nine kept; `Z`, `z`, `+`, `-` or `−` offsets up to 23:59),
the same order of checks and the same error text, so validation messages that
embed the parse error are unchanged. Additions, millisecond differences and
ordering match `chrono`, including overflow: a lease TTL longer than `chrono`
could hold counts as 60 seconds, a deadline past the range saturates to
`+262142-12-31T23:59:59.999999999+00:00`, and an over-long recovery grace keeps
`chrono`'s error. Lease TTLs are validated to 24 hours and idempotency
retention to 30 days, so those branches are not reachable from configuration.
Snapshot-date validation in `llm/capabilities` uses the same calendar.

One accepted difference, for an input IronCrew never writes: a leap second
(`:60`) reads as the last nanosecond of the preceding second; `chrono` kept it
as a separate instant and wrote it back as `:60`.

### Boundary: the remaining exception

`rmcp` 3.11 depends on `chrono` unconditionally (MCP model timestamps), so
`chrono` stays in `Cargo.lock` with `rmcp` as its only dependent. The
`RUSTSEC-2026-0543` exception in `.cargo/audit.toml` remains, narrowed to that
dependent, re-reviewed on 2026-11-22 and due again by 2026-12-20. The
repository-policy tests fail if the file ignores anything else, if any crate
other than `rmcp` resolves `chrono`, if the entry outlives that dependency, if
an IronCrew manifest table names `chrono`, or if code under `src/`, `tests/`,
`benches/` or `examples/` imports it.

### Validation

Parity was established against `chrono` itself. A scratch program outside the
repository linked `chrono` 0.4.45 and the new module and compared them:
2,000,000 random instants across `chrono`'s whole range, weighted toward the
present, the years 0000 to 9999 and both range ends (both written forms, lease
deadlines, second addition, millisecond differences and ordering);
3,197,568 parse inputs (mutations of valid timestamps plus every field
boundary); and every year 0000 to 9999 with months 0 to 13 and days 0 to 32 for
snapshot dates. There were 0 differences apart from the 115,884 leap-second
inputs. Values recorded from `chrono` are kept as unit tests in
`src/utils/timestamp/tests.rs`.

Validation on the change, all local on macOS: `cargo fmt --all -- --check`;
`cargo clippy --all-targets -- -D warnings`; `cargo test --all-targets`
(74 targets, 1,578 passed, 3 ignored, no database URL); `cargo test --doc`; the
module-size gate (six legacy ceilings lowered) and the Python policy tests;
`bun test scripts/tests/*.test.ts`; `./scripts/check-lua-examples.sh`; the
worktree whitespace check and the issue registry check.
`cargo audit --deny warnings` passes with the narrowed exception and fails on
`RUSTSEC-2026-0543` without it. `bun --no-env-file run scripts/check-postgres.ts`
passed all five suites (77 tests each) on disposable containers running
`postgres:17` (17.12) and freshly pulled `postgres:latest` (19.0), image
digests `sha256:223efeb196329b55b3b9a13db144956411dbc18e727e59f681c3e0aede6475cf`
and `sha256:fe9ef8058929c976110d4b75d9b939e61a590ba1e105e609e891c71bb39a8944`.
Windows and other platform-only CI jobs, the replica soak and deployed
environments were not run.
