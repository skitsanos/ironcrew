# IC-002 — Replica maintenance database waits are not bounded

## Outcome and validation

**Resolved locally on 2026-08-07.** PostgreSQL lease heartbeat,
reconciliation, keyed-heartbeat, and startup idempotency-prune transactions now
install transaction-local `lock_timeout` and `statement_timeout`. PostgreSQL
also advertises a larger Tokio watchdog that bounds pool acquisition,
transaction setup, and aggregate multi-statement latency. JSON and SQLite do
not use that cancellable wrapper, so their synchronous or `spawn_blocking`
work is never detached by this policy.

The periodic maintenance bit becomes unhealthy after the first bounded
heartbeat/reconciliation failure and recovers only after both operations
succeed in one cycle. Healthy in-flight work does not create transient
readiness failures. At startup, bounded PostgreSQL reconciliation or pruning
failure no longer prevents `/health/live` from binding; readiness reports
`503 storage_maintenance` until the normal loop recovers. Local backend prune
errors remain fail-fast.

Reconciliation now selects at most 64 runs per transaction, reserves 32 slots
each for expired pre-intent claims and existing runs, uses unused capacity for
the non-empty side, and scopes journal/idempotency/HITL writes to those IDs.
Conversation tombstones and mailbox cleanup have independent 64-row budgets.
The core transition remains atomic. If the outer watchdog wins before its
commit, SQLx rollback-on-drop preserves all-or-nothing behavior; a timeout in
the later best-effort journal-prune transaction cannot undo already-committed
run recovery.

On disposable PostgreSQL 15, six focused maintenance regressions passed,
including held advisory and row locks, full pool saturation, 130 mixed expired
runs, and three cumulative 500 ms statements that force outer cancellation
without a partial commit. The complete `postgres_store_test` passed 44/44. The
real process target passed 1/1 in 24.36 seconds and proved a held startup quota
lock yields live `200`, ready `503 storage_maintenance`, then ready `200` after
release; the same run also proves normal owner-death reconciliation. Exact
all-target Clippy passed. This is local database/process evidence, not a
Railway or OpenShift routing test.
