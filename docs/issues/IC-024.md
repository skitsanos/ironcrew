# IC-024 — Tool-sandbox documentation misstates http availability

## Finding

`docs/tools.md` states in three places (around lines 286-295, 519, and 521-526)
that custom Lua tools "cannot call `http.*` directly" because "the `http` global
is not registered in the tool sandbox", and builds a workaround section on that
premise (delegate via `run_flow`, fetch in `crew.lua`, or use the `http_request`
tool). This is false. Custom tool VMs are built by
`create_tool_lua_with_execution_policy`, which calls
`register_lua_globals_with_policy` (`src/lua/sandbox.rs`), and that function
registers the `http` table unconditionally. The registry test at
`src/tools/registry/tests/lua.rs` runs a custom tool whose `execute` calls
`http.post(...)` and fails on the HTTP body-size policy — proving the global is
present and callable, not nil. A stale in-code comment in `src/lua/sandbox.rs`
("http ... will need to be wired in a future iteration") matches the outdated
doc.

The consequence is a security-posture misstatement: an operator reading the docs
will believe custom tools are network-isolated, when in fact they can reach the
network (subject to the SSRF/body-size policy).

## Outcome and validation

**Resolved on 2026-08-19.** The documentation was the stale side and has been
corrected to match the implemented, tested contract: custom Lua tools *can* call
`http.*`, governed by the outbound-network policy (SSRF validation plus the
response body-size limit captured when the tool is created). The registry test
`src/tools/registry/tests/lua.rs` exercises exactly this path, so removing the
capability would have broken a deliberate behavior and any user tool relying on
it.

Changes: `docs/tools.md` replaces the "Tools cannot call `http.*`" claim and its
workaround framing with an accurate description of the capability and its
limits; the Lua-globals isolation table now lists `http` for the tool sandbox
(and correctly identifies `require` as the crew-only global); the `run_flow`
section no longer describes itself as bypassing an `http` restriction. The stale
"will need to be wired in a future iteration" comment in `src/lua/sandbox.rs`
now states where `http` is registered and that `llm` remains per-execution.

Validation: no code behavior changed. `cargo test --all-targets` (55 binaries,
0 failures) and `scripts/check-lua-examples.sh` (65 files) confirm the described
contract still holds.

Boundary: this records the capability truthfully so operators can reason about
it. Reviewers should treat a custom Lua tool as network-capable; an approval
gate on the built-in `http_request` tool does not constrain `http.*` calls made
from inside a custom tool.
