# IC-016 — Staged HITL key rotation lacks a replica acceptance gate

## Outcome and validation

**Resolved locally on 2026-08-10.** PostgreSQL store startup now checks every
retained question and answer fingerprint against the immutable process keyring.
The check has transaction-local lock/statement timeouts and an outer deadline
derived from `IRONCREW_DB_CONNECT_TIMEOUT_SECS`; a process missing any retained
key fails before binding HTTP. It is deliberately a startup snapshot rather
than a recurring full-table readiness query.

Answer delivery now selects and authenticates the retained encrypted question
under the existing run/idempotency/row fences before it can mutate the row. The
answer is encrypted with that question's fingerprint, not the responding
process's active key. Therefore a new-active peer can answer an old-key question
without stranding its old-active owner. A process whose startup snapshot
preceded a stale old-key write still fails the operation without changing the
pending row. Question-list decryption and answer-side question authentication
share the bounded `IRONCREW_HITL_PG_MAX_CONCURRENT_READS` semaphore.

The provider-free separate-process gate rolls two real `ironcrew serve`
processes through old-only, expanded/old-active, expanded/new-active, and
new-only configurations against disposable PostgreSQL 15.18. The final focused
run passed 1/1 in 9.62 seconds after five earlier stabilization passes. It
proved:

- premature new-only startup is rejected while an old-key question remains,
  and the failed list/answer attempt leaves ciphertext and routing state exact;
- old questions receive old-key answers during both old-active and mixed-active
  overlap, while a new-active owner later creates new-question/new-answer rows;
- every accepted answer is consumed once, each durable journal has exactly one
  request/receipt/terminal sequence, and duplicate answers return `404`;
- both fingerprint columns contain zero old references only after every live
  process selects the new active key, after which both new-only processes start;
  and
- answer/key canaries remain absent from SQL plaintext, durable/shared SSE,
  audit metadata, HTTP error bodies, and stopped-process logs. The authenticated
  question-list response intentionally contains its prompt.

A live store regression independently covers a post-startup stale writer,
question-only and answer-only startup rejection, pinned answer fingerprints,
no-mutation failure, and zero-row retirement success. The final serial
PostgreSQL set passed 2/2 multi-replica HTTP, 45/45 store, and 7/7 genuine
two-process tests. Cleanup left zero phase-two relations or replica sessions.

This closes the same-binary, direct-port, local PostgreSQL rotation contract.
At this issue's resolution, cross-version binary compatibility, platform secret
propagation, load-balanced routing, owner execution failover, and Railway/
OpenShift rollout inventory were still assigned to IC-007. IC-007's later
Railway/OpenShift canaries replayed the accepted same-binary three-revision
sequence and closed that platform claim; cross-version compatibility and owner
execution failover remain unsupported.
