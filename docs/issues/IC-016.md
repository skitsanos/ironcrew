# IC-016 — Staged HITL key rotation lacks a replica acceptance gate

## Required outcome and acceptance

The keyring unit tests prove that an expanded keyring can decrypt ciphertext
written with an old key while encrypting new payloads with the selected active
key. The genuine two-process PostgreSQL target, however, starts every process
with the same single-key configuration. It does not prove the documented
two-stage Railway/OpenShift rotation remains readable while old and new
revisions overlap and pending encrypted questions survive restarts.

Required outcome:

- create pending old-key question and answer ciphertext before rotation;
- roll two real processes through an expanded old-active keyring, then through
  a new-active keyring, without ever introducing a reader that lacks a key a
  writer may select;
- prove both revisions can list, answer, and consume retained ciphertext exactly
  once while fingerprints identify the expected key and plaintext stays absent
  from SQL, logs, audit metadata, and SSE;
- drain or expire every row that references the retiring fingerprint before the
  old key is removed, and fail closed if removal is attempted too early; and
- record disposable PostgreSQL 15 process evidence separately from the platform
  routing and secret-rollout canary owned by IC-007.

Acceptance must exercise mixed process revisions and real stored mailbox rows;
constructing two keyring values in one unit test is necessary but not sufficient.
