# IC-005 — Owner death during durable cancellation lacks an acceptance gate

## Outcome and validation

**Resolved locally on 2026-08-07.** Two separate-process PostgreSQL 15 cases
now inject real owner death at both missing boundaries. The pre-pickup case
confirms A is stopped, records cancellation through B, proves A's lease does
not renew, and sends `SIGKILL`. The post-pickup case holds the exact global
idempotency-quota advisory lock, waits for A's cancellation-pickup log and a
`pg_stat_activity` blocker relationship, then kills A before its terminal
transaction can commit.

Both cases reconcile the single run to `Abandoned` with A's owner id, a cleared
lease, one completed ledger, and no shared HITL row. The ledger retains the
original `200` response and `cancel_requested_at` as historical evidence; the
timestamp is not active control state. Durable event counts do not change,
there is no stored `run_complete`, and repeated SSE reads each receive one
unnumbered fallback marked `journal_complete: false`. Concurrent same-key
requests replay the exact original acceptance, and a stale A-owned success
write returns `AlreadyTerminal(Abandoned)` without changing the snapshot.

The focused target passed 2/2 in 22.86 seconds and cleanup left zero phase-two
tables. The ordinary pre-pickup path sampled B ready before cancellation,
after `SIGKILL`, and after reconciliation. The deliberate global-lock case can
correctly make storage maintenance unready while contention is injected, so
its contract is recovery to ready after lock release, which passed. Exact
all-target Clippy passed. This is local process/database evidence, not a
Railway or OpenShift signal-routing gate.
