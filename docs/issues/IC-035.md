# IC-035 — Silent degradation on malformed tool arguments and failed hooks

## Finding

Two paths degrade silently instead of surfacing a recoverable error:

- `src/engine/executor.rs` parses provider tool-call arguments with
  `serde_json::from_str(...).unwrap_or(Object::new())`. A provider that emits
  truncated or invalid JSON arguments has the tool executed with empty arguments
  — for example `file_read` with no path — producing a confusing tool-level error
  attributed to the tool, or a defaulting tool doing the wrong thing, instead of
  a "malformed arguments" tool result the model could self-correct from.
- `src/engine/executor/hooks.rs` returns the original text on any hook load or
  run failure with only a `tracing::warn!`. Because `func.dump(false)` strips
  upvalues and the hook VM lacks the sandbox globals (`json_parse`, `log`, `env`,
  and similar) that were in scope where the hook was authored, a hook referencing
  any of them fails on every invocation while the run proceeds as though hooks
  applied. Operators get no run-visible signal that their hooks are dead.

## Required outcome and acceptance

Malformed tool arguments must produce an explicit tool result (for example
`Tool error: invalid JSON arguments`) rather than an empty-argument execution, so
the model can retry. Hook failures must be visible in the run surface (a
`CrewEvent::Log` or metric, not only a tracing warning); ideally hooks execute in
the environment they were authored in, which also addresses IC-021. Add
regression coverage for a malformed-arguments tool call and for a hook that fails
to load being reported rather than silently skipped.

### Status note — 2026-08-19

Not yet implemented. The related sandbox work in [IC-021](./IC-021.md) is
complete, and hook load failures now go through a single `load_hook` helper in
`src/engine/executor/hooks.rs`, which is the natural place to emit the
run-visible signal this issue asks for. The malformed-tool-argument half is
independent and unaffected.

## Outcome and validation

Resolved on 2026-09-20. The task executor, reusable agent-turn loop, and dialog
tool loop now reject malformed provider tool arguments before timeout selection
or registry dispatch, append the bounded `Tool error: invalid JSON arguments`
result to the active tool-call turn, and let the model retry. Regression
coverage proves that registered tools are not executed and the follow-up task
provider request receives the explicit result.

Hook VM initialization, execution-guard, environment, load, runtime, and
invalid-return failures now increment the process-local fixed-cardinality
`ironcrew_hook_failures_total{hook,stage}` counter exposed by authenticated
`GET /metrics`. Hooks remain fail-soft: the original task description or output
is retained. The invalid-bytecode regression proves the load failure increments
the metric, and the authenticated metrics contract proves all 12 fixed
hook/stage combinations are exposed. The public hook example no longer calls a
crew global unavailable inside the isolated hook VM, and the REST/deployment
guidance documents the metric and alerting boundary.

The executor's bounded prompt builder moved into a focused module, reducing the
legacy executor from 484 to 405 lines. Agent-turn tool dispatch moved into a
focused module, reducing that legacy module from 644 to 594 lines; repository
policy ratchets both lower ceilings. Validation passed with formatting, strict
Clippy, all-target Rust tests, no-default-features and locked release builds, doctests,
RustSec audit, module-size policy, 76 repository-policy Python tests, 66 Lua
example validations plus five offline probes, and the crew-effectiveness
contract (74 evaluator tests, 36 CLI runs, 96 mock requests, 72/72 grounded
answers). Live PostgreSQL validation was not run because this change does not
touch storage, schemas, leases, HITL persistence, journals, or replica
coordination.
