# IC-023 — Default memory value cap rejects valid task output and fails the run

## Finding

Task output is accepted up to `IRONCREW_TASK_RESULT_MAX_OUTPUT_BYTES`, default
8 MiB (`src/engine/orchestrator.rs`), and foreach combined output up to the same
bound (`src/engine/foreach.rs`). End-of-phase persistence then writes every
successful result into the memory store via `crew.memory.set(...).await?`
(`src/engine/orchestrator.rs`), and foreach does the same
(`src/engine/foreach.rs`). `MemoryStore::set` rejects any value larger than
`IRONCREW_MEMORY_MAX_VALUE_BYTES`, default 1 MiB
(`src/engine/memory.rs`, `validate_item_input`).

Because the persistence error is propagated with `?`, any task or foreach whose
output lands between ~1 MiB and 8 MiB executes successfully — provider tokens are
spent and `TaskCompleted` is emitted — and then the whole `run_crew` returns a
Validation error, discarding all results and marking the run Failed. Under
default configuration this is a silent, expensive footgun: the caps are
inconsistent and the failure surfaces only after the paid work is done.

## Outcome and validation

**Resolved on 2026-08-19.** End-of-phase memory persistence is now best-effort.
`src/engine/orchestrator.rs` logs a warning and emits a `CrewEvent::Log` when a
task result cannot be stored, instead of propagating the error with `?` and
failing a run whose provider work already succeeded; `src/engine/foreach.rs`
does the same for foreach output. This matches the pre-existing treatment of
`memory.save()` failures, so persistence problems are reported uniformly rather
than aborting completed work.

Regression coverage: `tests/memory_cap_run_survival_test.rs` runs a crew whose
task emits 2 MiB — above the 1 MiB default `IRONCREW_MEMORY_MAX_VALUE_BYTES`,
below the 8 MiB default `IRONCREW_TASK_RESULT_MAX_OUTPUT_BYTES` — and asserts
the run reaches a successful terminal state with the full output returned to the
caller intact.

Validation: `cargo test --all-targets` (55 binaries, 0 failures), clippy clean.

Boundary: the two caps remain independently configurable and are unchanged; an
oversized value is still not persisted to memory, it simply no longer discards
the run. Operators who need such values in memory should raise
`IRONCREW_MEMORY_MAX_VALUE_BYTES`.
