# IC-019 — Per-replica admission scope lacks a saturation acceptance gate

## Outcome and validation

**Resolved locally on 2026-08-09.** A new provider-free acceptance gate runs
three sequential pairs of real `ironcrew serve` operating-system processes
against disposable PostgreSQL 15.18. Each pair uses explicit small limits and
direct A/B ports so process and shared-store behavior cannot be confused by a
load balancer.

The first pair holds one run, one resident conversation, and one run SSE
connection on A. A then returns the documented run/conversation `503` and SSE
`429`, while an initially idle B reports zero active work and independently
admits one of each before reaching the same limits. The second pair configures
burst-one work, control, and observation buckets. Each process records exactly
one admitted and one limited request per class, while A's exhausted bucket has
no effect on B. The third pair sets the shared PostgreSQL idempotency record and
in-flight limits to one: A fills the ledger, and distinct keys through both A
and B receive durable `429` without preventing question polling or peer
cancellation.

Every applicable `429` has numeric positive `Retry-After` and
`Cache-Control: no-store`; run/conversation semaphore exhaustion remains
`503`. Per-target metric scrapes distinguish local active/limit gauges,
token-bucket decisions, and quota-rejection observations from identical shared
durable usage. The gate rejects API tokens, principals, owners, run IDs, raw
idempotency keys, database coordinates, table prefixes, and keyring material in
metric output. Direct SQL confirms one hashed ledger row and no raw key.

While implementing the gate, exact structural run-control route matching
replaced substring classification, so attacker-controlled flow or conversation
IDs named `abort`/`answer` cannot consume the more permissive control bucket.
Run and conversation SSE now share the same non-cacheable, non-buffered success
contract, and saturated conversation SSE receives the documented hardened
`429` response.

The checked-in capacity arithmetic now multiplies process-local run,
conversation, SSE, PostgreSQL-pool, and platform-memory settings by replica
count. The Lua formula is explicitly only a top-level root-VM budget: nested
`run_flow`/`crew:subworkflow` VMs, Rust/event/provider allocations, and RSS are
additional. Run task-slot arithmetic is likewise not a cluster-wide provider
semaphore.

After replacing a registration-timing assumption with a bounded durable-mailbox
barrier, four consecutive focused runs passed in 6.67, 6.42, 6.63, and 6.41
seconds. The complete separate-process target passed 6/6 in 59.54 seconds. The
complete PostgreSQL target set then passed 2/2 multi-replica HTTP tests, 44/44
store tests, and 6/6 process tests. Cleanup left zero prefixed relations,
functions, or IC-019 replica backends before the disposable database was
removed.

This resolves the direct-process/local-PostgreSQL saturation gate. It does not
measure cgroup/RSS capacity, nested-flow peak memory, provider traffic,
autoscaling, gateway/global admission, drain behavior, or Railway/OpenShift
routing. At this issue's resolution those boundaries were assigned to IC-018,
IC-020, and IC-007. The later IC-020 and IC-007 closures supplied their bounded
lifecycle and platform evidence, and IC-018 later supplied its predeclared
provider-free local retention-boundary receipt. None of those results turns
host-process measurements into cgroup, autoscaling, or live-provider proof.
