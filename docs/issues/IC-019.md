# IC-019 — Per-replica admission scope lacks a saturation acceptance gate

## Required outcome and acceptance

Documentation states that active-run, conversation, and SSE semaphores plus
principal token buckets are process-local while durable idempotency quotas are
shared, so aggregate capacity is `replicas × per-replica limits`. The
two-process gate raises work-admission limits to focus on replay behavior and
never demonstrates this split under saturation, even though the deployment
matrix requires it before scale-out.

Required outcome:

- run two real processes with deliberately small, explicit active-run,
  active-conversation, SSE, and work/control/observation admission limits
  against disposable PostgreSQL 15;
- independently saturate those process-local limits on replica A and require
  `429` for token-bucket, SSE, or durable-quota denial and `503` for an
  exhausted run/conversation semaphore, including the documented `Retry-After`
  and `Cache-Control` headers where their contracts apply, while idle replica B
  retains only its own configured process capacity;
- exhaust a shared idempotency quota and prove both replicas observe the same
  durable rejection without weakening control or observation admission;
- verify protected metrics distinguish each process's active work and admission
  outcomes from shared durable usage, without high-cardinality identities; and
- document and assert aggregate memory, provider, SSE, and PostgreSQL pool math
  as replica count multiplied by the configured per-process limits.

This gate proves the current scope; global admission or autoscaling is a separate
capability, and real platform routing remains under IC-007.
