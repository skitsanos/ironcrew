# IC-061 — MCP discovery silently overwrites ambiguous tool identities

## Finding

Distinct valid server/tool pairs can produce the same registry name: server `a`
with tool `b__c`, and server `a__b` with tool `c`, both become `mcp__a__b__c`.
Discovery inserts directly into the tool registry, silently replacing an earlier
tool. Server iteration order can determine which execution identity is selected.
An existing registered MCP tool can also be replaced by a later manager.
Programmatic Rust configurations can repeat a server label; the connection map
then retains only the last server under that label.

HTTP tool discovery already rejects duplicate server-local names, but stdio
accepts them within a page and across pages. This permits another silent
replacement when the manager registers the returned definitions.

Synthetic, provider-free stdio regressions in `tests/mcp_tool_identity_test.rs`
confirm all four failures before the correction. A control case confirms that
distinct names containing underscores remain supported.

## Outcome and validation

Bounded tool listing rejects duplicate server-local names, including pagination,
poisons the failed connection and reaps its child. The manager checks configured
labels before connecting, then stages every composed tool name against the whole
batch and the existing registry before registering anything. A collision closes
only the new connections and leaves the existing identities and tools usable.

Valid names and production deadlines are unchanged. This intentionally rejects
formerly ambiguous configurations; rename the conflicting server label or tool.
The contract and migration guidance are recorded in `docs/crews.md`,
`docs/tools.md` and `examples/mcp/stdio-tools/README.md`.
