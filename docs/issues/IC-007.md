# IC-007 — Railway and OpenShift replica routing lacks platform evidence

## Required outcome and acceptance

Local PostgreSQL and separate-process gates do not prove Railway's public
routing, injected port, deployment overlap, signal window, private networking,
or OpenShift Service/Route behavior under a restricted security context. The
current multi-replica contract therefore cannot be promoted to platform truth.

Required outcome:

- deploy two independently observable replicas sharing one PostgreSQL schema,
  unique instance IDs, the same release artifact and flow set, authentication
  and idempotency policy, table prefix/schema, runtime limits, and HITL keyring;
- record immutable revision, flow/config fingerprints, and non-secret effective
  settings so normal replica parity is demonstrated rather than assumed;
- demonstrate load-balanced same-key replay, conflict, cancellation, encrypted
  HITL, and retained run SSE without affinity;
- restart or replace an owner during bounded work while the peer remains ready;
- after IC-016's local mixed-process gate passes, execute its ordered old-key,
  expanded-keyring, new-active-key, and retirement sequence during a real
  overlapping platform rollout, proving every writer has compatible readers;
- execute the scale-up, drain, scale-down, and rolling-replacement platform
  canary owned by IC-020, including the draining-owner control boundary;
- record routing distribution, status/body, owner IDs, terminal rows, resource
  limits, and non-secret platform logs; and
- run an equivalent OpenShift restricted-SCC/Route canary or explicitly keep
  OpenShift unverified if no cluster is available.

The result must distinguish intentional rollout differences from accidental
configuration drift, a temporary canary from long-duration production
monitoring, and must not claim live conversation portability or execution
takeover.
