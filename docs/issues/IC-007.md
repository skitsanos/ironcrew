# IC-007 — Railway and OpenShift replica routing lacks platform evidence

## Outcome and validation

Local PostgreSQL and separate-process gates did not prove Railway's public
routing, injected port, deployment overlap, signal window, private networking,
or OpenShift Service/Route behavior under a restricted security context. The
multi-replica contract therefore required dated platform evidence before it
could be promoted beyond local process truth.

The accepted outcome is cumulative and keeps each evidence class explicit:

- two independently observable replicas shared one PostgreSQL schema per
  platform, unique process identities, the same attested v7 binary and flow,
  authentication/idempotency policy, explicit runtime limits, and compatible
  HITL keyrings;
- immutable revision, binary/flow/config/keyring fingerprints, complete
  non-secret effective settings, and per-start identities were independently
  verified rather than inferred from advertised strings;
- retained Railway evidence and authoritative OpenShift v7 demonstrated
  load-balanced replay, conflict, cancellation, encrypted HITL, and retained
  run SSE without affinity;
- bounded Railway/OpenShift owner replacement kept the peer ready, while
  OpenShift additionally exercised real owner `SIGKILL` and reconciliation;
- IC-016's accepted expanded/old-active, expanded/new-active, zero-old-
  reference, and new-only sequence during a real overlapping platform rollout,
  compatible readers, intended key revisions, and zero old references passed
  on both platforms;
- IC-020's scale, drain, scale-down, and rolling-replacement canaries passed,
  including the draining-owner control boundary;
- the receipts retain route distribution, status/body, owner/process IDs,
  terminal rows, resource-limit arithmetic, and bounded non-secret scans; and
- OpenShift v7 passed the complete applicable matrix under `restricted-v2`
  through an affinity-free Route.

The independent final cleanup audit also passed. All attributable Railway and
OpenShift database/platform/local resources returned to their declared
baselines without a broad delete or Docker prune. The evidence below
distinguishes intentional platform/rotation differences from drift, retains
superseded negative attempts, and does not claim a published or reproducible
artifact, live conversation portability, execution takeover, general
exactly-once external effects, or the long IC-018 retention-boundary soak.

### Railway sandbox

host-process RSS was unavailable, so these numbers are not an OOM or sustained

## IC-020 lifecycle canary evidence — 2026-08-10

The follow-up lifecycle gate used the same provider-free flow
(`sha256:5c1df07adad7493ed580cde11256b2c8df7b49d84d13d74c539191d6464bb691`)
on both platforms. Railway used Linux binary
`sha256:0a9f7c66d745c6c8c87985a38d5067a6d42d5e9b0b66c74efe383dda15ae8867`;
OpenShift used the corrected follow-up binary
`sha256:8c430f064523e7f1ceba4c4da97fbd26f4bcfce9eef3f2bc6b2d87a91a50d3c4`
after the first OpenShift rollout exposed readiness-probe contention. These
were reviewed dirty-worktree artifacts, not published release images.

Railway scaled `1 -> 2 -> 1`, mapped authenticated IronCrew identity headers
to both runtime Railway replica IDs, and exercised exact-owner `SIGUSR1` and
`SIGTERM`. Direct mutations and peer control returned the documented draining
errors; the held run persisted one `Aborted` terminal event; same-key replay
retained its run and owner; and the in-place restarted process completed a
second peer-answered HITL run. Railway kept routing some reads to the drained
process and reused the same replica ID after restart, so this is application
fencing evidence rather than ingress-withdrawal or replacement-identity proof.

OpenShift ran corrected replicas under `restricted-v2` as UID `1004800000`.
The gate proved `1 -> 2 -> 1`, EndpointSlice withdrawal, peer drain rejection,
clean PID 1 termination, one `Aborted` terminal event, and stable replay. The
first rolling attempt exposed contention-only readiness `503`s; bounded
readiness singleflight plus `minReadySeconds: 10` corrected them. The final
homogeneous rollout kept the stable peer ready, passed 64/64 parallel readiness
per corrected replica, and returned 60/60 readiness, 60/60 liveness, and 60/60
capability responses through the affinity-free shared Route. A retiring
deployment-specific route still produced one lifecycle `503` and one timeout,
so only the shared route with a ready peer is claimed continuous.

Both canaries recorded bounded RSS/pool/platform limits and found no exact
canary credentials in their scoped logs/database/reports. Railway returned to
zero active services, instances, volumes, buckets, domains, and proxies; its
deleted canary volume remains an asynchronous tombstone beside the untouched
pre-existing tombstone. OpenShift dropped every prefixed database object,
deleted all 14 labeled objects, restored quota use to zero, and reproduced the
25-object shared-namespace baseline byte-for-byte.

IC-020 is resolved by this lifecycle evidence. At that checkpoint, IC-007 kept
conservative Railway owner-death/SIGKILL, staged-key, repeated-feature, and
effective-config blockers. The authoritative evidence above reconciles that
checkpoint with the literal issue outcome: OpenShift v7 supplies the complete
applicable matrix and real `SIGKILL`; retained Railway receipts supply owner
replacement and the previously accepted routed surfaces; Railway v7 supplies
the missing real-overlap rotation and per-process config attestation. It does
not claim that Railway repeated every case under v7. Live conversation
portability and execution takeover remain explicitly unsupported, while the
long resource boundary remains IC-018.
