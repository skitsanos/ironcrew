# IC-021 — Hook and condition Lua evaluation escapes the crew sandbox

## Finding

The crew VM is sandboxed in `create_crew_lua_with_policy`
(`src/lua/sandbox.rs`): it is built with a restricted standard library, `os` is
trimmed to `clock/time/date/difftime`, `loadfile`/`dofile` are removed, and
shell access is gated on `IRONCREW_ALLOW_SHELL`. That sandbox is bypassed by two
sibling evaluation paths that construct a raw VM:

- `src/engine/executor/hooks.rs` builds the hook VM with `mlua::Lua::new()`.
- `src/engine/condition.rs` builds the condition VM with `mlua::Lua::new()`.

In mlua 0.12, `Lua::new()` opens `StdLib::ALL_SAFE`, which still includes `io`,
`os`, and `package`, and `load_chunk` accepts binary chunks with no safe-mode
gate. `before_task`/`after_task` hook bodies are dumped to bytecode in the
sandboxed VM (`src/lua/crew_userdata.rs`) and re-loaded here, and task
`condition` strings are arbitrary Lua from the flow definition evaluated via
`evaluate_condition` (`src/engine/orchestrator.rs`). Concretely, a flow with
`condition = 'os.getenv("OPENAI_API_KEY") ~= nil'`, or a hook calling
`io.open`/`os.execute`/`os.exit`, runs with full process privileges — the exact
capability the sandbox and the AGENTS.md "treat Lua as untrusted" rule remove.
Secondary defect: both VMs are thread-locals reused across runs on the same
Tokio worker with shared globals, so one flow's hook/condition can persist state
that another flow later reads (cross-run leakage in server mode).

## Outcome and validation

**Resolved on 2026-08-19.** Hook bytecode and task conditions no longer run in a
default mlua VM. `create_eval_lua` (`src/lua/sandbox/eval_vm.rs`) builds the
evaluation VM with the same restricted standard library as the crew VM —
`STRING | TABLE | MATH | COROUTINE | OS`, `os` trimmed to
clock/time/date/difftime, `loadfile`/`dofile` removed — and both
`src/engine/executor/hooks.rs` and `src/engine/condition.rs` now use it.

Cross-run leakage is closed by `fresh_eval_environment`: every hook call and
every condition evaluation runs with its own environment table whose `__index`
falls through to the VM globals, so reads of the standard library still work
while writes are discarded when the evaluation ends. The condition evaluator
binds `results` into that per-call environment instead of the shared globals.

Regression coverage (9 tests) asserts that hooks and conditions cannot resolve
`io`, `os.execute`, `os.getenv`, `os.exit`, `os.remove`, `package`, `require`,
`loadfile`, or `dofile`; that `os.time`/`os.clock` remain available; and that a
global written by one evaluation is not visible to the next. A separate probe
confirmed the pre-fix baseline: a raw `mlua::Lua::new()` VM does expose `io`,
`os.execute`, `os.getenv`, and `package`, so the tests discriminate.

Validation: `cargo test --all-targets` (55 binaries, 0 failures),
`cargo clippy --all-targets` clean, `cargo fmt --check` clean,
`scripts/check-lua-examples.sh` (65 files, 5 offline probes),
`scripts/check_module_size.py` passing.

Boundary: this restores the sandbox for flow-supplied expressions. It does not
give hooks access to crew globals (`json_parse`, `log`, `env`); hook bytecode is
dumped without upvalues and could not reach them before this change either. See
[IC-035](./IC-035.md) for making such hook failures visible.
