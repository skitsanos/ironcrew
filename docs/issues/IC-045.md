# IC-045 — Validate does not evaluate crew construction without effects

## Finding

`cmd_validate` in `src/cli/commands.rs` checks project declarations but only
compiles `crew.lua` with `into_function()`. Inline constructors, unknown keys,
model option combinations, and dynamically assembled dependency graphs are
not exercised. [IC-028](./IC-028.md) deliberately left no-effect evaluation
as follow-on work; its runtime unknown-key fix remains resolved.

## Outcome and validation

**Resolved locally on 2026-09-20.** `ironcrew validate --evaluate` now runs
bounded construction evaluation using the production Crew/Agent/task parsers,
conversation/dialog builders, dependency graph validator, and IC-044 policy.
The default declaration/syntax mode and HTTP validation endpoint are unchanged.

The evaluator reads one immutable, bounded, no-follow Lua/SQL source snapshot.
Config and entrypoint evaluation share a restricted VM; separate agent/tool
declaration VMs match the production loader's isolation while sharing the
instruction, time, and admitted-declaration budgets. Captured crews are exposed
through construction-only userdata. No executable crew/session handle, store,
provider request, tool invocation, or synthetic execution result reaches Lua.
Persistent declarations are checked without reading or creating their stores.
Credentials and `.env` are not needed for this mode.

Exit `0` means the evaluated construction path passed; `1` means invalid
construction or a source/resource/worker failure; `2` is a CLI usage error;
`3` means incomplete construction requiring execution/external state, unsupported
capabilities, or no constructed crew. Graph/reference errors discovered before
an execution boundary still fail validation. Dynamic callbacks and untaken
branches are explicitly outside the proof. MCP discovery, nested execution,
environment access and stored state are never replaced with fabricated values.

Lua memory, aggregate instructions, stack depth, option-table depth/entries,
retained strings/bytecode and crew/declaration counts are capped. A supervised
worker enforces a 10-second hard deadline even inside native Lua operations;
a lifetime pipe terminates it when its supervisor is cancelled or killed.
Diagnostics are bounded. Protected calls, finalizers and dynamic loading are
unavailable in this restricted mode. Secure source capture currently requires
Unix; other platforms fail closed. The exact limits and unsupported patterns
are documented in [the CLI contract](../cli.md#validate).

Five existing examples separate construction from paid execution and now run
under `--evaluate` in the repository/CI Lua gate. CLI help, model-policy docs,
mode-guard guidance and the examples catalog distinguish construction evidence
from provider/runtime evidence. New production modules stay below 300 lines;
constructor support and binary tests were extracted, lowering the reviewed
`api.rs` and `main.rs` ceilings instead of growing those legacy modules.

The accepted requirements were:

- Add a documented bounded construction-evaluation mode to `ironcrew validate`
  using the real constructors/parsers and [IC-044](./IC-044.md) capability rules.
- Validate evaluated agent/task/dialog/conversation options and constructed
  dependency graphs, including unknown references and cycles, before paid work.
- Prevent provider requests, network access, database effects, process spawning,
  file writes, and execution-triggered side effects throughout project loading
  and evaluation, including config files, imports, callbacks, and nested flows.
  Bound CPU/instructions, memory, recursion, and permitted project reads.
- Do not fabricate successful execution results to drive unknown branches.
  Report unsupported effect-dependent construction or unvalidated paths
  explicitly; define exit statuses so CI cannot mistake partial validation for
  complete validation. Document the limit of inspecting dynamic Lua.
- Cover misspelled keys, unsupported effort/model combinations, invalid graphs,
  infinite loops, effect attempts, and an ordinary valid project. Assert no
  external calls or writes occur, including on error and cancellation.
- Integrate the appropriate mode into example/CI validation and reconcile CLI
  help, workflow docs, and example expectations.

## Dependencies and boundaries

Package 2, depends on IC-044. This validates construction, not provider behavior,
task output quality, every possible Lua branch, or deployed runtime behavior.
The existing static checks must not be represented as stronger evidence.
