# IC-046 — Token accounting omits reasoning detail and incomplete-attempt coverage

## Finding

`TokenUsage` and `TaskTokenUsage` expose prompt, completion, total, and cached
counts but no reasoning-token detail. Responses parsing discards that detail.
Task execution aggregates successful tool rounds but its error/retry return
path does not retain complete attempt usage. Conversations and delegated work
also need an explicitly defined aggregate accounting contract before a shared
run budget can depend on their receipts.

Evidence: `src/llm/provider.rs`, `src/llm/openai_responses.rs`,
`src/engine/task.rs`, `src/engine/executor.rs`, `src/engine/task_runner.rs`,
and the Lua conversation/agent-turn paths.

## Implementation progress

Started on 2026-09-20 after committing IC-045 as `485d7fc`. The current source
confirms the finding: provider parsers use zero fallbacks and narrowing casts,
Chat Completions streaming drops usage, and task retries discard earlier
attempts. PostgreSQL run totals also use signed 32-bit columns. The first
implementation slice is a checked receipt/parser/aggregate foundation; wiring
provider attempts, cancellation, public outputs and durable records remains
required before this issue can close. No budget enforcement is in this slice.

The new `ironcrew::usage` library foundation now provides:

- Explicit `complete`, `partial` and `unavailable` receipts, optional 64-bit
  counts, reasoning/cache-write detail, checked relationships and validated
  receipt serialization. No missing receipt becomes known zero.
- Constant-space OpenAI Chat/Responses and Anthropic usage parsers, preserving
  cumulative streaming snapshots and known partial subtotals. Anthropic input
  normalization includes both cache categories. Official-field references and
  measurement boundaries are recorded in [usage accounting](../usage-accounting.md).
- Atomic checked aggregates with per-field completeness, plus a shared
  process-local attempt guard that settles once on normal completion or future
  drop. Overflow during drop stays visible as an error, rather than returning
  an old apparently complete snapshot.

The foundation was committed as `24296b2` after the complete local gate below.
The follow-on HTTP capture layer now connects explicit request scopes to all
three built-in providers. Guards begin at dispatch, observe usage before output
decoding or streaming awaits, and settle on normal completion, failure or future
cancellation. Chat streaming requests usage; Responses captures terminal
failed/incomplete receipts; Anthropic retains cumulative cache/output detail.
HTTP error receipts and accounting overflow remain visible.

This is not a compatibility adapter around old counts. `ChatResponse.usage`,
task/event outputs and storage still require replacement, and the runtime does
not yet automatically share scopes across retries/conversations/delegation.
Custom providers do not automatically participate. Loopback transport and
explicit-scope cancellation/parallel tests do not prove executor ownership,
PostgreSQL, process-death recovery, multi-replica execution or budget enforcement.

Provider stream/output decoding and request configuration were split into
focused modules. The binary's server-address resolution was extracted when
adding its shared usage import. All new production modules are under 300 lines;
four stale legacy exceptions were removed and the fixed cap ratcheted 46 to 42.

The original end-to-end requirements remain:

- Define a checked aggregate usage representation with optional reasoning-token
  detail and explicit complete, partial, or unavailable coverage. A missing
  provider receipt must not be reported as a known zero-cost request.
- Parse supported provider usage in streaming and non-streaming paths and
  document each provider's semantics. Do not double-count reasoning or cached
  subsets in totals. Verify current fields against official documentation.
- Retain known usage across tool rounds, retries, failure, cancellation, parallel
  tasks, conversations, and nested/delegated work without double-counting.
- Expose consistent usage/coverage in relevant CLI, Lua, HTTP, events, and durable
  run records. Unknown usage remains visibly unknown after serialization.
- Add fixtures for full, missing, malformed, partial-stream, and large/overflow
  counts, plus aggregate tests spanning a failed attempt and successful retry.
- Update usage docs with measurement boundaries; token receipts are not invoices.
