# IC-046 — Token accounting omits reasoning detail and incomplete-attempt coverage

## Finding

`TokenUsage` and `TaskTokenUsage` expose prompt, completion, total, and cached
counts but no reasoning-token detail. Responses parsing discards that detail.
Task execution aggregates successful tool rounds but its error/retry return
path does not retain complete attempt usage. Conversations and delegated work
also need an explicitly defined aggregate accounting contract before a shared
run budget can depend on their receipts.

Evidence: `src/llm/provider.rs`, `src/llm/openai_responses.rs`,
`src/engine/task.rs`, `src/engine/executor.rs`, `src/engine/task_runner.rs`,
and the Lua conversation/agent-turn paths.

## Implementation progress

Started on 2026-09-20 after committing IC-045 as `485d7fc`. The current source
confirms the finding: provider parsers use zero fallbacks and narrowing casts,
Chat Completions streaming drops usage, and task retries discard earlier
attempts. PostgreSQL run totals also use signed 32-bit columns. The first
implementation slice is a checked receipt/parser/aggregate foundation; wiring
provider attempts, cancellation, public outputs and durable records remains
required before this issue can close. No budget enforcement is in this slice.

The new `ironcrew::usage` library foundation now provides:

- Explicit `complete`, `partial` and `unavailable` receipts, optional 64-bit
  counts, reasoning/cache-write detail, checked relationships and validated
  receipt serialization. No missing receipt becomes known zero.
- Constant-space OpenAI Chat/Responses and Anthropic usage parsers, preserving
  cumulative streaming snapshots and known partial subtotals. Anthropic input
  normalization includes both cache categories. Official-field references and
  measurement boundaries are recorded in [usage accounting](../usage-accounting.md).
- Atomic checked aggregates with per-field completeness, plus a shared
  process-local attempt guard that settles once on normal completion or future
  drop. Overflow during drop stays visible as an error, rather than returning
  an old apparently complete snapshot.

The foundation was committed as `24296b2` after the complete local gate below.
The follow-on HTTP capture layer now connects explicit request scopes to all
three built-in providers. Guards begin at dispatch, observe usage before output
decoding or streaming awaits, and settle on normal completion, failure or future
cancellation. Chat streaming requests usage; Responses captures terminal
failed/incomplete receipts; Anthropic retains cumulative cache/output detail.
HTTP error receipts and accounting overflow remain visible.

Provider capture was committed as `77569b6`. This is not a compatibility adapter
around old counts. `ChatResponse.usage`, task/event outputs and storage still
require replacement. The following execution phase adds automatic process-local
ownership; neither phase proves PostgreSQL, process-death recovery, multi-replica
execution or budget enforcement.

Provider stream/output decoding and request configuration were split into
focused modules. The binary's server-address resolution was extracted when
adding its shared usage import. All new production modules are under 300 lines;
four stale legacy exceptions were removed and the fixed cap ratcheted 46 to 42.

The current execution phase introduces explicit provider scope binding. Each
Lua execution VM shares a tracker across crews, conversations, dialogs, retries,
parallel/foreach/collaborative work and delegated agents. Nested flow and Lua-tool
VMs inherit it; separate top-level VMs stay isolated even with a shared Runtime.
Rust embedders can retain a bound tracker after success, failure or cancellation.
Opaque custom-provider invocations count as unavailable unless the implementation
opts into checked receipt ownership. Existing old usage fields are not used as
a compatibility fallback. Child results are not re-added to inclusive totals.

The latest checkpoint adds hierarchical run/session views and read-only Lua
`crew:usage()`, `crew:flow_usage()`, `conversation:usage()` and `dialog:usage()`
snapshots. A crew keeps only its latest executing run scope; prior snapshots are
detached. Children update ancestors exactly once with bounded nesting and
atomic checked settlement. Decimal-string counts and explicit nulls preserve
the full unsigned range through JSON and Lua; checked deserialization rejects
inconsistent coverage and malformed counts. No old-count conversion is added.

That checkpoint was committed as `098a16b`. At that boundary, per-task attribution,
result-field migration, durable checkpoints and historical session usage remained
required. Focused helper
extractions shrink six touched legacy modules and keep every new module below
300 lines. Execution validation is recorded below.

### Final completion: provider returns, metrics and session checkpoints

The direct-provider return contract now requires a checked `UsageReceipt`.
All built-in streaming/non-streaming paths preserve optional unsigned counts,
coverage, reasoning and cache details without narrowing or unknown-to-zero
fallbacks. Dispatch guards emit usage telemetry exactly once on success,
failure and cancellation, even for unscoped direct calls. Runtime wrappers
respect provider-owned telemetry; fixed-cardinality metrics expose known token
lower bounds, receipt coverage and incomplete fields. Operational metric
counters are not exact billing records.

Conversation and dialog handles retain an independent session tracker seeded
from the durable checkpoint. New attempts update both the active caller's run
scope and the session observer atomically; shared ancestors are deduplicated,
and historical receipts are never charged to a newly resumed run. Immutable
observer ancestry is bounded and uses a consistent lock order. Resetting the
transcript does not reset usage.

JSON, SQLite and PostgreSQL persist checked session snapshots alongside history
under existing revision/CAS and idempotency transactions. All backends reject
forged or in-flight checkpoints; SQL readers bound the payload before returning
it. SQL migration marks old records unavailable without inventing receipts;
old JSON records lacking the required usage contract are unsupported. CLI chat
`/usage`, Lua session methods, HTTP message/history responses and conversation
summaries expose the same checked snapshots. Peer reads and cold rehydration
preserve them. The public and deployment documentation describes these changes.

Failed/cancelled turn usage remains in the live handle and is included in the
next successful save. Eviction or process death before that save can lose
unsaved receipts: this is checkpoint persistence, not a crash-safe billing
journal. Restored historical unknown coverage remains unknown.

The original end-to-end requirements, now satisfied within these boundaries:

- Define a checked aggregate usage representation with optional reasoning-token
  detail and explicit complete, partial, or unavailable coverage. A missing
  provider receipt must not be reported as a known zero-cost request.
- Parse supported provider usage in streaming and non-streaming paths and
  document each provider's semantics. Do not double-count reasoning or cached
  subsets in totals. Verify current fields against official documentation.
- Retain known usage across tool rounds, retries, failure, cancellation, parallel
  tasks, conversations, and nested/delegated work without double-counting.
- Expose consistent usage/coverage in relevant CLI, Lua, HTTP, events, and durable
  run records. Unknown usage remains visibly unknown after serialization.
- Add fixtures for full, missing, malformed, partial-stream, and large/overflow
  counts, plus aggregate tests spanning a failed attempt and successful retry.
- Update usage docs with measurement boundaries; token receipts are not invoices.
