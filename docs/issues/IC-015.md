# IC-015 — Release automation admitted ambiguous tags and non-cascading Docker triggers

## Outcome and validation

### Historical local outcome — 2026-08-07

Local remediation on 2026-08-07 addressed the original tag ambiguity,
over-broad workflow permissions, unsafe release-note transport, imprecise
Cosign identity guidance, and the non-cascading Docker trigger. Before that
work, the release-source guard checked version and `main` ancestry but accepted
lightweight tags, while the release workflow granted contents-write and OIDC
authority to guard and build jobs. Published verification guidance used a
repository-prefix certificate regular expression, and arbitrary tag
annotations were transported through a fixed workflow-output delimiter. Docker
publication also listened for a release event that cannot be caused by the
preceding `GITHUB_TOKEN`-authenticated release action.

The guard now requires an annotated stable `vX.Y.Z` tag before checking the
manifest version and `main` ancestry. Guard and matrix builds have contents-read
only; the final publication job alone receives contents-write and OIDC. Release
notes are written to a runner-temporary file consumed through `body_path`, and
the generated Cosign command binds verification to the exact repository,
`release.yml`, and tag identity.

Docker publication is manual-only, accepts one required exact stable tag through
an environment variable, verifies that it names a published non-draft,
non-prerelease GitHub release, and runs only when dispatched from the default
branch. Dispatches are serialized, and a fresh API check precedes a possible
`latest` update. Release guidance records the explicit second authorization and
the non-cascading `GITHUB_TOKEN` boundary.

Repository-policy tests cover job permissions, annotation rejection, release
body transport, exact certificate identity, manual Docker dispatch, safe input
handling, the presence of the pre-update `latest` check, and isolation from
global Git signing configuration. The Bun policy suite, adversarial
signing-config regression, `actionlint`, `bash -n`, `shellcheck`, skill
validation, issue-registry validation, and `git diff --check` passed locally on
2026-08-07. No release, Docker image, tag, or remote configuration was created
or changed during that validation. Platform-enforced tag rules, branch
protection, and release environment approval remain tracked under IC-014.

### Regression revalidation — 2026-08-11

The 2026-08-07 controls remain useful, but current source does not support the
historical immutability and rollback-prevention conclusions:

- `.github/workflows/docker-publish.yml` unconditionally includes the stable
  `${version}` destination in the build-and-push tag list. It does not inspect
  the registry for an existing version tag or compare its digest before the
  push. Re-dispatching an accepted historical release therefore makes an
  unconditional attempt to move that public version tag; the repository does
  not prove whether an external Docker Hub immutability rule rejects it.
  Workflow serialization alone does not make the tag immutable.
- The workflow checks out the current dispatch revision from the default
  branch and uses its current workflow and `docker/runtime.Dockerfile`, rather
  than binding the runtime recipe to the verified release tag. The signed
  release binaries are downloaded for the requested tag, but the Dockerfile
  starts from moving `debian:13-slim` and installs from moving package indexes.
  A later dispatch for an old release can therefore wrap the same signed binary
  in a changed recipe, base, package set, or image metadata and attempt to
  publish that result under the old version tag.
- The GitHub latest-release API check and the registry retag operation are
  separate operations. A newer release can become current after the check but
  before `docker buildx imagetools create` runs, allowing the older dispatch to
  attempt to move `latest` backwards with no repository-side post-write check
  or repair. The current workflow concurrency group does not serialize GitHub
  release creation with that registry update.
- The repository-policy tests assert workflow shape and input handling, but do
  not exercise an existing registry version tag, a historical build after the
  default branch or base image changes, or a concurrent newer release during
  the `latest` update.

This revalidation reopens IC-015. It does not invalidate the dated local test
results above; it narrows what those structural checks proved.

### Local publication-protocol checkpoint — 2026-08-12

The local implementation removes image rebuilding from the manual
Docker publisher. The tag-triggered release workflow checks out the exact tag
commit and builds one `linux/amd64` plus `linux/arm64` OCI archive from the
already checksummed release binaries. The runtime recipe uses the
content-addressed Wolfi base index
`sha256:30f03343947c7ae3581fda727a6e2aa7b8ce7009b7bfc2ab8d5c9483ace5812f`
without a moving package-install step. A strict receipt binds the tag, commit,
source timestamp, Dockerfile hash, base reference and digest, binary archive
hashes, OCI archive and index digests, platform manifests and configurations,
and builder identity. The archive and receipt are checksummed and signed as
tag-owned release assets. Release creation and Docker promotion share the
`release-publication` concurrency group, and release publication refuses an
existing release instead of updating or replacing its assets.

The manual publisher now requires both an exact stable release tag and an
explicit latest-reconciliation authorization. It downloads the signed OCI
archive and receipt, verifies their checksums, exact tag-bound Cosign workflow
identity, strict receipt contents, and authenticated Docker Hub immutable-tag
configuration, then promotes the archive without rebuilding it. An absent
version tag is copied and read back, an identical existing digest is a no-op,
and a different existing digest fails closed. `latest` reconciliation reads
the current GitHub stable release before and after each registry write and can
repair a concurrent change to another release carrying the complete signed
IC-015 asset set, with three attempts as the workflow bound.
Policy and executable regressions cover replay, conflicting existing digests,
receipt and OCI archive structure, moving-base rejection, and a newer release
appearing during `latest` promotion.

At the initial 2026-08-12 checkpoint, live read-only checks showed that the
required external boundary was not yet satisfied. GitHub's current stable
release was `v2.22.0`, published on
2026-07-07. Docker Hub reported `immutable_tags_settings.enabled: false` with
the inactive rule `.*`. Its `latest` and `2.20.0` tags both resolved to
`sha256:fa336f85a0347001438d576f2e945136eb40485f7a6a0355a77ea0dbf38230c6`,
while `2.21.0` and `2.22.0` returned `404`; the public `latest` alias was
therefore behind GitHub's current stable release. These observations are a
dated snapshot, not a repository guarantee.

### Non-production registry acceptance — 2026-08-12

The production Docker Hub repository now enforces only the exact stable-semver
immutability rule required by the publisher. `latest` remains mutable. A
post-change registry snapshot confirmed that `latest` and `2.20.0` still point
to the pre-existing
`sha256:fa336f85a0347001438d576f2e945136eb40485f7a6a0355a77ea0dbf38230c6`
index while `2.21.0` and `2.22.0` remain absent. The operation changed policy
only; it did not publish or move a production image or tag.

The disposable repository
`skitsanos/ironcrew-ic015-acceptance-20260812t115900z-5fd204be` then passed the
real Docker Hub protocol with two distinct pinned multi-platform indexes. It
proved initial `0.0.1` publication, identical replay as a no-op, protocol-level
conflict refusal, direct Docker Hub rejection of a conflicting overwrite,
same-archive mutable-tag write/restore controls, `0.0.2` publication, and a
two-attempt `latest` repair from the injected older
release to the newer one. The exact final tag inventory was
`0.0.1`, `0.0.2`, and `latest`. Authenticated API absence plus registry lookups
proved the disposable repository and all three tags removed afterward.

The sanitized machine receipt is
[`2026-08-12-ic015-dockerhub.json`](../../evaluations/release-acceptance/reports/2026-08-12-ic015-dockerhub.json),
SHA-256
`6635719fcda499cadc3a076182f7c7ab3b00cd19f362edbcd6781636bc9e2a11`.
It binds the exact harness files, source indexes, phase-receipt hashes,
production policy, unchanged production tag snapshot, and cleanup boundary.

The protocol begins with the first release produced by this tag workflow; it
does not backfill legacy releases such as `v2.22.0`, which do not contain the
new signed OCI archive and receipt. An externally created or incomplete newer
GitHub release also fails promotion closed rather than being treated as
eligible for `latest`. Preventing such an untrusted release-authority action is
the separate IC-014 platform-control boundary.

The shared concurrency group prevents simultaneous release/promotion mutation,
but the repository-pinned actionlint does not yet recognize GitHub's newer
multi-pending-run queue syntax. This change therefore does not claim durable
queueing of bursts: GitHub can replace an older pending run, which an operator
must redispatch. That is an availability boundary, not permission to replace a
published release asset or semantic-version digest.

registry inspector, acceptance harness, retained receipt, and documentation.
The first platform run exposed an unrelated IC-017 acceptance-test timing

The focused predicate regression, exact Clippy, the complete local all-target
Rust suite, and five live PostgreSQL 15 IC-017 runs passed; both named `--rm`
containers were verified removed.

The exact-head platform run
[`31596627801`](https://github.com/skitsanos/ironcrew/actions/runs/31596627801)
then passed all nine jobs: formatting/Clippy/tests, Windows compile, repository
policy, macOS tests, crew-effectiveness contract, release build, Lua examples,

closes IC-015's repository and non-production registry acceptance. No
production image, tag, GitHub release, or release asset was published. Docker
publication remains deferred under IC-014's independent platform-control
boundary and the user's release-last sequence.
