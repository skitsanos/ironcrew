# IC-015 — Release automation admitted ambiguous tags and non-cascading Docker triggers

## Required outcome and acceptance

### Historical local outcome — 2026-08-07

Local remediation on 2026-08-07 addressed the original tag ambiguity,
over-broad workflow permissions, unsafe release-note transport, imprecise
Cosign identity guidance, and the non-cascading Docker trigger. Before that
work, the release-source guard checked version and `main` ancestry but accepted
lightweight tags, while the release workflow granted contents-write and OIDC
authority to guard and build jobs. Published verification guidance used a
repository-prefix certificate regular expression, and arbitrary tag
annotations were transported through a fixed workflow-output delimiter. Docker
publication also listened for a release event that cannot be caused by the
preceding `GITHUB_TOKEN`-authenticated release action.

The guard now requires an annotated stable `vX.Y.Z` tag before checking the
manifest version and `main` ancestry. Guard and matrix builds have contents-read
only; the final publication job alone receives contents-write and OIDC. Release
notes are written to a runner-temporary file consumed through `body_path`, and
the generated Cosign command binds verification to the exact repository,
`release.yml`, and tag identity.

Docker publication is manual-only, accepts one required exact stable tag through
an environment variable, verifies that it names a published non-draft,
non-prerelease GitHub release, and runs only when dispatched from the default
branch. Dispatches are serialized, and a fresh API check precedes a possible
`latest` update. Release guidance records the explicit second authorization and
the non-cascading `GITHUB_TOKEN` boundary.

Repository-policy tests cover job permissions, annotation rejection, release
body transport, exact certificate identity, manual Docker dispatch, safe input
handling, the presence of the pre-update `latest` check, and isolation from
global Git signing configuration. The Bun policy suite, adversarial
signing-config regression, `actionlint`, `bash -n`, `shellcheck`, skill
validation, issue-registry validation, and `git diff --check` passed locally on
2026-08-07. No release, Docker image, tag, or remote configuration was created
or changed during that validation. Platform-enforced tag rules, branch
protection, and release environment approval remain tracked under IC-014.

### Regression revalidation — 2026-08-11

The 2026-08-07 controls remain useful, but current source does not support the
historical immutability and rollback-prevention conclusions:

- `.github/workflows/docker-publish.yml` unconditionally includes the stable
  `${version}` destination in the build-and-push tag list. It does not inspect
  the registry for an existing version tag or compare its digest before the
  push. Re-dispatching an accepted historical release therefore makes an
  unconditional attempt to move that public version tag; the repository does
  not prove whether an external Docker Hub immutability rule rejects it.
  Workflow serialization alone does not make the tag immutable.
- The workflow checks out the current dispatch revision from the default
  branch and uses its current workflow and `docker/runtime.Dockerfile`, rather
  than binding the runtime recipe to the verified release tag. The signed
  release binaries are downloaded for the requested tag, but the Dockerfile
  starts from moving `debian:13-slim` and installs from moving package indexes.
  A later dispatch for an old release can therefore wrap the same signed binary
  in a changed recipe, base, package set, or image metadata and attempt to
  publish that result under the old version tag.
- The GitHub latest-release API check and the registry retag operation are
  separate operations. A newer release can become current after the check but
  before `docker buildx imagetools create` runs, allowing the older dispatch to
  attempt to move `latest` backwards with no repository-side post-write check
  or repair. The current workflow concurrency group does not serialize GitHub
  release creation with that registry update.
- The repository-policy tests assert workflow shape and input handling, but do
  not exercise an existing registry version tag, a historical build after the
  default branch or base image changes, or a concurrent newer release during
  the `latest` update.

This revalidation reopens IC-015. It does not invalidate the dated local test
results above; it narrows what those structural checks proved.

### Remaining required outcome

- Make version publication immutable at the registry or publication-protocol
  boundary. A repeated historical dispatch must fail closed or prove the
  existing digest is identical and perform a no-op; a check followed by an
  unconditional mutable push is insufficient.
- Bind image publication to immutable release inputs: use the verified release
  tag's source and recipe plus content-addressed base/dependency inputs, or
  promote an image digest produced and recorded for that release. A historical
  dispatch must not rebuild from the current default branch or moving package
  state.
- Close the `latest` time-of-check/time-of-use window with coordination that
  spans release selection and registry mutation, or with post-write
  revalidation and deterministic repair. A stale dispatch must never leave
  `latest` pointing behind GitHub's current latest stable release.
- Add policy and executable tests for repeat publication of an existing
  version, a changed default-branch/build-input replay, and a newer release
  appearing during the `latest` update. Preserve the existing annotated-tag,
  exact-release, least-privilege, signature-identity, and separate-authorization
  controls.
- Record one non-production end-to-end registry acceptance run that proves the
  version-tag replay and concurrent-`latest` cases. Until those controls and
  evidence exist, keep Docker release publication deferred and do not describe
  version aliases as immutable or the `latest` update as rollback-proof.
