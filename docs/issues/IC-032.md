# IC-032 — Taskfile publish can overwrite signed release images

## Finding

`Taskfile.yaml` targets `docker-build-multi` and `docker-publish` build from the
root `Dockerfile` (rust builder to `debian:13-slim`) and `--push` both
`skitsanos/ironcrew:{{VERSION}}` and `:latest`. The governed release path
(`.github/workflows/docker-publish.yml`) states publication never rebuilds an
image from a checkout and promotes only the signed Wolfi-based OCI archive from
`docker/runtime.Dockerfile` (digest-pinned, in sync with `release.yml`
`BASE_IMAGE_INDEX_DIGEST`).

A stray `task docker-publish` from a developer machine overwrites the released
tags with an unsigned image built from a different base, bypassing the
IC-014/IC-015 hardened promotion path. IC-014/IC-015 hardened the workflow; this
local escape hatch survived.

## Outcome and validation

**Resolved on 2026-08-19.** Local Task targets can no longer overwrite released
images. `Taskfile.yaml` introduces a separate `DEV_IMAGE`
(`skitsanos/ironcrew-dev`); `docker-build` tags only that image locally,
`docker-build-multi` pushes only that image, and the `:latest` tag is no longer
produced or pushed by any local task. `docker-publish` now announces that it is
pushing a development image and does not publish a release. `docker-run` uses
the development tag it builds.

The released tags remain exclusively owned by the signed promotion workflow in
`.github/workflows/docker-publish.yml`, which promotes the attested OCI archive
built from the digest-pinned `docker/runtime.Dockerfile`. A header comment in
`Taskfile.yaml` records that boundary so the escape hatch is not reintroduced.

Validation: `task --list` resolves all five targets with the updated
descriptions; no CI workflow or script references these targets, so retargeting
them affects local use only.

Boundary: this removes the accidental-overwrite path. It does not add a
technical control on Docker Hub itself; registry-side tag immutability remains
the concern of IC-014/IC-015 tooling.
