# IC-028 — Unknown Lua configuration keys are silently ignored

## Finding

The Lua configuration surface reads known keys and ignores everything else.
`Crew.new` (`src/lua/api.rs`), agent and task parsing (`src/lua/parsers.rs`), and
the conversation/dialog option tables (`src/lua/conversation.rs`,
`src/lua/dialog.rs`) all `get`/`raw_get` specific keys; a misspelled or
unsupported key name silently no-ops. Values of known keys are strictly
validated, but a typo in a key name is not caught anywhere. This is
security-relevant for `require_approval`: a table written as `require_aproval`
disables the approval gate with no warning. The same mechanism lets examples
teach fields that do not exist (see the MCP examples passing `role`, `backstory`,
`max_iter`, which `agent_from_lua_table` never reads).

The gap is not caught by `ironcrew validate`, whose `cmd_validate`
(`src/cli/commands.rs`) compiles the entrypoint into a function but never
executes it, so inline configuration tables are never evaluated.

## Outcome and validation

**Resolved on 2026-08-19.** Unknown configuration keys are rejected instead of
silently ignored. `reject_unknown_keys` (`src/lua/parsers.rs`) compares a
table's string keys against a closed accepted set and fails with a message
naming the offending keys and listing the supported options. It is applied to
agent tables, task tables, and `Crew.new` (which also covers `config.lua`
through the defaults merge). Array parts and runtime-injected `__ironcrew*` keys
are exempt.

The accepted sets (`AGENT_KEYS`, `TASK_KEYS`, `CREW_KEYS`) were derived by
extracting every key the parsers actually read, and cross-checked against the
documented option tables in `docs/crews.md`.

This closes the security case in the finding: a misspelled `require_approval`
now fails crew construction rather than quietly leaving the approval gate off.

Regression coverage asserts that CrewAI-style `backstory`/`max_iter` on an agent
are rejected with a message pointing at `system_prompt`, that a misspelled
`dependson` is rejected with `depends_on` named, that every documented agent
option is still accepted, and that array parts and internal keys do not trip the
check.

Examples and documentation: the two MCP examples that passed the nonexistent
`role`, `backstory`, and `max_iter` fields were rewritten to use
`system_prompt`; `docs/crews.md` documents the strict-key contract.

Validation: `cargo test --all-targets` (55 binaries, 0 failures), clippy clean,
`scripts/check-lua-examples.sh` (65 files validated, 5 offline probes passed).

Boundary: this is a deliberate behavior change — a flow that previously carried
an ignored key now fails at construction with an explicit message. Options
belonging to a provider you are not using remain accepted and unused. The
`validate` command still does not execute `crew.lua`, so these errors surface at
run time rather than during validation; a no-effect evaluation mode for
`validate` remains open follow-on work.
