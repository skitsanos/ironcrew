# IronCrew 4.0.0

Status: prepared on `develop`; not yet tagged, published, or deployed.
This document covers changes since the published `v3.0.0` release.

IronCrew 4 makes crew construction easier to check before a paid run and makes
provider usage visible even when work fails. It adds shared token budgets,
parameterized PostgreSQL operations for flow authors, and bounded live-provider
smoke tooling. This is a major release because the public usage and persistence
contracts intentionally replace the v3 shapes without compatibility adapters.

## Breaking changes and upgrade checklist

### Usage results, events, and stored history — IC-046 / IC-047

- `TaskResult.usage` replaces `token_usage`. Run records, summaries and
  `run_complete` replace top-level `total_tokens` / `cached_tokens` with `usage`.
  Update CLI-output consumers, Lua scripts, HTTP clients and event handlers.
- Counts in public JSON/Lua usage snapshots are decimal strings, not JSON
  numbers; unavailable counts are `null`, not zero. Snapshots distinguish
  complete, partial and unavailable receipt coverage and require `budget` state.
  Do not add child usage to an already inclusive parent total.
- Export/archive existing run and session history and back up databases before
  upgrading. Old JSON records and old task-result payloads without checked
  `usage` are unsupported. SQL upgrades mark missing checkpoints unavailable;
  they do not reconstruct receipts from legacy token counters. Old SQL columns
  remain untouched but are no longer used by the new accounting path.
- Drain active work before switching versions. Do not assume mixed v3/v4
  writers or rollback against an upgraded store are supported. Validate the
  upgrade on a disposable copy; retain the pre-upgrade backup for recovery.
- Rust embedders must update result/receipt types and custom providers. Custom
  providers must explicitly own checked receipt capture and, for budgeted
  execution, admission; an opaque provider cannot claim complete accounting.

See [usage accounting](../usage-accounting.md) for persistence and session
checkpoint limits, and [token budgets](../token-budgets.md) for admission rules.

### PostgreSQL support window

- The minimum supported PostgreSQL major is now **17**, retained throughout
  IronCrew 4.x. Each IronCrew major chooses the older of the two latest stable
  PostgreSQL majors available when it ships as its floor. New PostgreSQL
  releases do not raise an existing IronCrew major's floor; increases belong
  in the next IronCrew major's breaking changes. This is not a rolling
  two-major limit or an upper-version cap. See the
  [support policy](../storage.md#postgresql-support-policy).
- The runtime refuses older servers at connect time. Upgrade PostgreSQL 15/16
  deployments before installing 4.0.0 — the v3 → v4 store upgrade is not
  supported on an unsupported server.

### Configuration and failure behavior — IC-021 / IC-022 / IC-028 / IC-035 / IC-042–045

- Unknown Lua constructor keys and invalid enum/model-option combinations are
  rejected instead of being silently ignored. Run `ironcrew validate` and,
  on supported Unix hosts, `ironcrew validate --evaluate` on each flow; the
  latter is needed to exercise inline construction.
- Missing, empty or whitespace-only final model replies fail tasks/turns rather
  than becoming successful output. Dialogs stop on blank replies. Tool side
  effects already performed are not rolled back or silently replayed.
- Shell commands no longer inherit the full process environment. Review any
  required non-secret variables against `IRONCREW_SHELL_ENV_PASSTHROUGH`;
  `IRONCREW_*` variables cannot be re-admitted. Hook/condition evaluation is
  sandboxed, malformed tool arguments are reported, and hook failures are visible.
- The default model is `gpt-5.6-luna`. Its omitted effort resolves to `low`, or
  `none` for Chat Completions function tools. `minimal` is not a supported Luna
  default. Explicit unsupported choices fail rather than being rewritten.

## New capabilities

### Checked usage and shared token budgets — IC-046 / IC-047

Provider receipts include reasoning detail, cache categories and unsuccessful
attempts. Hierarchical scopes cover retries, parallel/foreach work, dialogs,
delegated agents and subflows without double-counting inclusive totals.

`IRONCREW_MAX_RUN_TOKENS` enables a shared input-plus-output admission ceiling.
It is disabled when unset. Initially it supports native OpenAI Responses without
provider-hosted tools; unsupported transports fail before generation when the
budget is enabled. Standalone HTTP conversation messages each receive a fresh
request budget. This is not a currency cap, a distributed account quota, or an
in-flight billing journal that survives process loss.

### Construction checks and model compatibility — IC-044 / IC-045

`ironcrew validate --evaluate` checks the evaluated Lua construction path with
the production parsers, graph checks and shared model-capability policy, without
credentials, provider calls or database writes. Work is bounded; exit code `3`
means incomplete/unsupported construction, not a successful validation. Dynamic
callbacks and untaken branches remain outside the proof. The default static
mode and HTTP validation endpoint remain unchanged.

Agents can override reasoning effort. A shared capability catalog drives both
offline validation and provider request construction; custom endpoints do not
inherit official model semantics merely from a model name.

### Parameterized PostgreSQL app data

Top-level `crew.lua` can call named operations from reviewed `sql/*.sql` files
through `postgres.query`, `postgres.query_one` and `postgres.execute`. Parameters
are bound, JSON uses native JSONB codecs, and multi-statement writes are
transactional and bounded. Enable this separately with
`IRONCREW_APP_DATABASE_URL` and a least-privilege app-data role.

This is distinct from IronCrew's run-history database. Database permissions,
not operation names, constrain flow authors. Sub-flow access and an agent-facing
PostgreSQL wrapper are not included. See [PostgreSQL app data](../postgres-app-data.md).

### Opt-in live-provider compatibility smoke — IC-048

A bounded four-case harness exercises Luna through basic CLI execution,
streaming dialogs, two-agent terminal HITL and keyed single-process HTTP HITL.
It checks outputs, token receipts, stop reasons, approvals and denials. Regular
CI remains provider-free; paid manual runs and nightly activation require the
documented opt-ins and protected credentials. Nightly activation remains off.

## Reliability, security, and maintenance

- Structured-output handling, Responses image attachments, provider deadlines,
  streaming/error handling and redaction are corrected (IC-025–027 / IC-033–034).
- Foreach failure gating, storage error status codes, HTTP transport limits,
  proxy attribution, CORS and audit coverage are tightened (IC-023 / IC-030–031 /
  IC-036).
- Blocking persistence/inspection work is moved away from Tokio workers;
  PostgreSQL storage is decomposed into domain modules, and the module-size
  ratchet remains enforced (IC-029 / IC-037 / IC-040).
- No-default-features builds work again; current examples, docs, dependency
  freshness checks and the fail-closed pre-push gate are maintained
  (IC-024 / IC-032 / IC-038–041).

## Release baseline and evidence boundary

- Minimum Rust toolchain: **1.98.1**.
- Dependency freshness was checked on 2026-09-21. The 41 other direct packages
  are current; `sse-stream` remains at `0.2.6` because current `rmcp 3.4.0`
  exposes the `0.2` transport types, incompatible with `0.3`. A lockfile refresh
  changes no packages. Older transitive `matchit 0.8.4` and
  `generic-array 0.14.7` remain exactly pinned by current `axum` and
  `crypto-common`, respectively; they are not forced past upstream constraints.
- MCP: strictly **2026-07-28**, still the current published revision when checked
  on 2026-09-21 against the [official version index](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning).
  No legacy protocol fallback or new optional MCP extension is introduced.
- PostgreSQL CI runs all five integration suites on the floor image
  (`postgres:17`) and freshly pulled `postgres:latest`. CI and local pre-push
  now share `scripts/check-postgres.ts`, which requires both database URLs,
  validates the exact floor and a newer latest major before destructive tests,
  and runs all five suites serially on each. Provision freshly pulled images
  and record their versions/digests as described in the
  [check skill](../../.agents/skills/check-ironcrew/SKILL.md#postgresql-and-replica-gate);
  the runner does not discover or provision the latest release itself.
  Historical PostgreSQL 15 receipts keep their versions.
- The earlier [Luna smoke receipt](../../evaluations/live-smoke/reports/2026-09-21-luna.json)
  covers its recorded pre-version-bump source and binary, not a published v4
  artifact. Local tests, mock contracts and PostgreSQL process gates do not
  establish deployed Railway/OpenShift behavior for this candidate.

Promotion to `main`, the annotated `v4.0.0` tag, protected validate-only requests,
GitHub release publication and Docker promotion remain separate owner-approved
steps. Versioned image references in the source tree are publication targets,
not proof that those images are available.
